# 开发者声音（VOD）

VOD 负责把问题**讲清楚并送达**，不负责修复。目标：没到过现场的人读完就能复现、判断影响、决定优先级和验收口径。

**入口条件**：当前任务必须有 Issue/PR 来源，评论才能落到对的地方。Web「新建任务」等无来源任务只能产出成稿（平台没有新建 Issue 的能力）。

## 何时使用

用：

- 用户说「提个 Issue」「提个需求」「反馈问题」「记录缺陷」「把这个问题整理成 Issue」「在 Issue 里呈现一下」。
- 任务指令要求把发现的问题写入仓库 Issue。
- 需要把一段模糊现象补成可执行的问题单。

需求类（能力缺口）同样用三段式：问题写清现状与缺口，诉求写期望能力与验收点；不写实现方案。

不用：

- 用户只是在问「为什么会这样」——先回答，不要擅自发布。
- 当前任务没有 Issue/PR 来源却要新建 Issue——平台不支持新建，只交稿（见「发不出去时」）。
- 需要改代码修复——那是开发任务；VOD 只产出问题描述与诉求。

## 三条铁律

1. **每个结论有出处。** 代码引用到 `path:line`；日志/命令贴真实输出；版本/commit 用实际值。核实不了的写「待确认」并说明需要什么信息。不编造现象、影响、复现步骤。
2. **一条评论只讲一个问题。** 发现多个问题就拆开：先问用户发哪个，或分别整理。不要把「顺手发现的三个 bug」塞进一条评论。
3. **只评论，不改 Issue。** 只用 `flowloop issue comment`。不改标题/正文、不打标签、不关闭 Issue、不 @ 无关的人。

## 先收集事实

能自己查的不要问用户。按三段补齐：

- **问题**：什么现象、什么条件下出现、影响谁/什么场景、多严重。能量化就量化：频率、耗时、失败率、影响的数据量。
- **背景**：怎么发现的、最小复现步骤、环境与版本（`git rev-parse --short HEAD`、`flowloop version`、OS/运行时）、证据（`path:line`、报错原文、关键日志；截图请文字转述，评论只支持文本）、已排除的猜测。
- **诉求**：期望行为（写「应该怎样」，不是「你该改哪行」）、优先级 P0–P3 及理由、可验证的验收点 1–3 条、建议修复方向（可选，标「建议」）。

只缺一类信息时**一次问全**，只问缺的，不要连续追问。用户答不上来、或当前是非交互执行，就写进「待确认」，不要留空也不要猜。

## 写稿

模板、示例与自检见 [references/template.md](references/template.md)。硬性要求：

- 评论没有标题：首行用一句话（可加粗）说清「什么坏了 + 影响」。若是交给用户新建 Issue 的成稿，标题同样一行说清，不写「关于……的问题」。
- 小标题固定为 `## 问题`、`## 背景`、`## 诉求`，顺序不变。
- 先事实后判断；推测必须标「推测」并给出依据。
- 控制在一屏到两屏；长日志只贴失败前后关键行，其余给命令或文件路径。
- 代码、路径、版本用反引号；命令用代码块。
- 脱敏：token、cookie、私钥、客户数据、内网地址一律替换为 `<redacted>`。

## 直接呈现到 Issue

当前任务的 Issue/PR 来源由平台记录；下面的环境变量仅供参考（Issue/PR 触发时才有，可能为空）：

```bash
echo "${FLOWLOOP_ISSUE_REPO:-<unset>}#${FLOWLOOP_ISSUE_NUMBER:-<unset>} ${FLOWLOOP_SOURCE_KIND:-issue}"
```

- `FLOWLOOP_ISSUE_REPO` 形如 `owner/repo`；`FLOWLOOP_ISSUE_NUMBER` 是编号；`FLOWLOOP_SOURCE_KIND=pull` 表示 PR 来源。
- Issue 与 PR 都能评论；PR 来源的评论会落到 PR 对话里，不要另开 Issue。
- 环境变量为空不代表一定没有来源，以发布结果为准；不要为了查来源去改代码或翻数据库。

**发布时机**：用户明确说「提个 Issue / 贴到 Issue / 在 Issue 里呈现」时，整理完直接发；只是让你分析、或你自己发现的问题，先给稿，得到明确指令再发。

长文本必须走文件，避免 shell 转义破坏 Markdown：

```bash
report="${TMPDIR:-/tmp}/vod-report-$$.md"
cat > "$report" <<'EOF'
<整理好的三段式正文>
EOF

flowloop issue comment --text "$(cat "$report")"
```

成功输出 `issue comment posted`。随后报告投递位置：

- 有 `FLOWLOOP_ISSUE_REPO` 和编号：报告 `<repo>#<N>`（PR 用 `<repo>!<N>`）；GitHub 仓库可附 `https://github.com/<repo>/issues/<N>`（PR 用 `/pull/<N>`），GitCode 用 `https://gitcode.com/<repo>/issues/<N>`（PR 用 `/pulls/<N>`）。其它宿主只报编号，不猜链接。
- 环境变量缺失：只报「已评论到当前任务来源的 Issue」，不要编造链接。

## 发不出去时

| 现象 | 处理 |
|---|---|
| `FLOWLOOP_GOAL_ID not set — this command must run inside a goal's run`（对话/非任务环境） | 不发布。把成稿交给用户，说明当前环境无法代发。 |
| `goal has no issue source` | 不重试。说明当前任务不是 Issue/PR 来源，交稿让用户自己贴；或等任务由 Issue 触发后再发。 |
| HTTP 4xx/5xx、`domain has no git_credentials (the platform token)` | 原样转述 stderr 的关键句，不要换命令乱试、不要假装成功。 |
| 同一问题已经发过 | 默认不重复发；修正用「补充：」而不是整篇重发，除非用户明确要求。 |

平台没有「新建 Issue」的命令。不要用 `gh issue create` 等外部工具绕过；没有可评论的 Issue 时只交稿。

## 不要做

- 不把 Issue 当聊天窗口：不发进度、不发「收到」、不发寒暄。
- 不把「诉求」写成替维护者拍板的实现方案；方案最多放「建议修复方向」。
- 不替用户决定优先级：给建议和理由，让用户/维护者确认；用户已给就照用。
- 不泄露运行日志里的凭据与个人信息。

## 完成前自检

- [ ] 三段齐全，首行/标题能独立看懂。
- [ ] 关键事实有出处，或明确标了「待确认」。
- [ ] 复现步骤第三人能照做。
- [ ] 影响与优先级有依据。
- [ ] 只发了一条评论，只讲一个问题，已脱敏。
- [ ] 已回报 Issue/PR 位置；没发出去时说清原因。
