# 蓝本自迭代断链：根因确认记录

> 确认时间：2026-11-21
> 结论级别：**已确认（反汇编级证据 + 数据库证据 + 在线实验三重验证）**，非推测。
> 附属文档：`ouroflow自动升级流水线v2-四任务执行记录与问题诊断.md`（本文是其第三节「为什么训练任务没有触发蓝本优化与自迭代」的最终定论，替代原文的候选 A/B/C 推测）

---

## 一、TL;DR（根因链，一句话版）

**4 个「蓝本训练任务」从创建那一刻起就没有被编译成蓝本工作流**——蓝本编译只挂在手动「启动」端点上，而它们创建时直接就是 active 状态、从未走过该端点（`blueprint_node` 全表 0 行，finalization guard 日志中 `blueprint=0` 佐证）；于是训练分析跑完后，翻译器 `draftAutoProposals → proposeForkForChain` 去查「本目标的物化节点」查到 0 行，**静默返回：无提案、无日志**。蓝本自迭代从未启动过，而平台没有任何一条日志告诉你这件事。

## 二、证据链（按因果顺序）

### E1. 翻译器确实被调用了（排除"没触发"假设）

- 调用点：`RSIService.Analyze` 尾部（`0x552728`）无条件调用 `draftAutoProposals`（反汇编核实：Publish 事件与调用之间无分支门控）。
- 在线实验（11-21 11:09）：`PUT /logs/level → debug` 后 `POST /rsi/sessions/07f2df9f…/retry` 重放 opencode 的训练分析 → **round 5 生成**（trigger=manual_retry，findings 正常复算）——分析管道完整执行，翻译器在链路上。
- 但 debug 级别下**零日志**：`[rsi] auto-proposal drafted / for goal %s: %v`（成功/失败日志）、`[rsi] auto-proposal cap check failed`、`translator proposal skipped (rsi.max_auto_rounds)`——一条都没出现，说明执行走了某个**无日志的静默退出分支**。

### E2. 静默退出点定位（反汇编）

`draftAutoProposals`（`0x5528a0`）流程还原：

| 步骤 | 代码位置 | 行为 |
|---|---|---|
| 1. BlueprintService nil 检查 | `0x5528d0` `ldr x8,[x0,#16]; cbz → 0x552b40` | nil → **裸 `ret`，无日志**（对照：emergent 路径 `RecordInferShape` 的同字段 nil 检查会打 `Warnf("rsi: blueprint service not wired — emergent draft skipped")`，`0x550418`） |
| 2. 查 goal.blueprint_version_id | SQL `SELECT COALESCE(blueprint_version_id,'') FROM goal WHERE id=?`（`0x89fb4c`） | 空 → 静默返回；**我们的 4 个目标非空（9ae4d32f…），此关通过** |
| 3. autoRoundsCap 封顶检查 | `0x550500` + SQL `SELECT COUNT(DISTINCT blueprint_id) FROM blueprint_proposal WHERE created_by_id='rsi-translator' AND status IN ('pending','approved'…)`（`0x8b3623`） | 当前计数 = 0 < 默认上限，**此关通过**；超限才会打日志 |
| 4. `proposeForkForChain` | `0x552c08` | 见 E3 |

`proposeForkForChain`（`0x552e10`）流程还原：

| 步骤 | 代码位置 | 行为 |
|---|---|---|
| 1. `criticalTaskChain(workflow)` | `0x554220`，返回链长 | **链长 < 2 → `mov x0,xzr; ret` 静默返回**（`0x552e54: cmp x1,#2; b.lt`） |
| 2. 查物化节点 | SQL `SELECT sub_goal_id, node_key FROM blueprint_node WHERE goal_id=? AND COALESCE(sub_goal_id,'')!=''`（`0x8ad026`，97 字节） | **0 行 → 链条目全部无节点映射可对 → 什么补丁都构造不出来 → 静默返回** |
| 3.（有节点时）getVersion → parseSpecContent → 构造 fork 补丁 → CreateProposal → 日志 `[rsi] auto-proposal drafted for goal %s: %s` | `0x553224`+ | 走到这里才会有提案和日志 |

**三个静默退出点（blueprint 服务未接线 / 物化节点为空 / 链长<2）全部没有日志**——任何一条命中都无声无息。这正是「零日志 + 零提案」的原因。

### E3. 数据库实证：4 个目标从未编译过蓝本

- `SELECT count(*) FROM blueprint_node` → **0**（全表空，从未有任何目标物化过节点）。
- 17 个 goal 中只有这 4 个 train 目标 `blueprint_version_id` 非空——即全库所有「绑定蓝本」的目标全部未编译。
- daemon.log 全程：`compile|materialize|spawn child` **零命中**——编译代码从未执行过。
- finalization guard 日志反复打印 `… ask-human=0 blueprint=0 — no gate yet`——**平台自己的守卫一直在说这些目标没有蓝本节点**。

### E4. 编译为什么从未发生（根因的最上游）

反汇编调用图：

- 编译函数 `GoalService.compileBlueprintTx`（`0x50a4b0`）**全二进制只有一个调用方**：`GoalService.Activate`（`0x53907c`）。
- `GoalService.Activate` **全二进制只有一个调用方**：HTTP handler `activateGoal`（`0x68fcd4`）——即「手动把 backlog 目标启动」的那个端点。
- `GoalService.Create`（创建路径）的调用清单里**没有** compileBlueprintTx——创建时不编译。
- 这 4 个目标的活动日志只有 `created → commented → entered_review → review_ready`，**没有 activated 动作**；owner run 在创建后 0.05~1 秒内就被派发——它们**创建时直接就是 active 状态**，绕过了唯一的编译入口。

**结论：创建即 active 的蓝本目标 = 「只盖章、不编译」。** AI SHELL 是拿着蓝本描述当 prompt 自由编排的（owner + consult mention 派发），形态恰好像蓝本，但平台层面没有节点级的「计划图 vs 实际执行图」绑定。

### E5. 佐证：平台设计意图本来支持自动提案

- Web UI 蓝本详情页文案（web chunk 原文）：*「还没有提案。跑过几次绑定了本蓝本的任务后，训练分析会产出结构化建议」*——产品预期就是绑定任务跑完后自动出提案。
- `proposeForkForChain` 的存在本身说明翻译器只实现了**一条规则：把关键串行链分叉成并行泳道**（fork-for-chain），它天然只对结构类 finding（serial_chain / lost_parallelism）有效。即使节点物化了，**human_wait 类瓶颈（我们 4 个任务的最大发现，占 37%~91%）在这个 build 里也没有对应的翻译规则**——没有任何提案模板管它。

## 三、修复建议（按优先级）

1. **【必须】创建即 active 的路径接上编译**：`GoalService.Create` 在 status=active 且 blueprint_version_id 非空时应调用 compileBlueprintTx（或创建一律落 backlog、由激活端点统一编译——推荐后者，语义更清晰）。
2. **【必须】补观测性**：draftAutoProposals 的三个静默退出点（blueprints nil / 版本空 / 进入 proposeForkForChain 后链<2 / 节点映射 0 行）至少留一条 Debugf；goal 绑定了蓝本但 blueprint_node 为 0 行时，在 Analyze 完成时打一条 Warn（"goal %s 绑定蓝本但未编译——提案跳过"，这就是本次问题的直接可观测信号）。
3. **【建议】扩充翻译规则**：为 human_wait（把 gate 证据包固化成模板/自动通过+抽查）、lane_imbalance 等高频 finding 类别增加提案模板；当前 build 只有 fork-for-chain 一条规则，覆盖率太窄。
4. **【流程】找回 featnew 源码**：运行二进制构建自已删除的 `/tmp/ouroflow-featnew`（版本串 `0.1.0-featnew.20261119`，module `github.com/Sinkear/ouroflow`，无 vcs stamp），工作区 `/root/workspace/ouroflow-src` 是旧版（无 blueprint 模块）。上述 1-3 的修复都需要先在 GitCode/GitHub 上游仓库定位 featnew 对应的提交。
5. **【验证手段】**：修复合入后，新建一个蓝本目标（走 backlog→手动启动路径），确认 blueprint_node 有行、跑完 approve 后 daemon.log 出现 `[rsi] auto-proposal drafted`、`/blueprints/{id}/proposals` 出现 pending 提案。

## 四、对本环境 4 个历史目标的处置说明

- 已 done，无法追溯编译（编译发生在激活时，事后无法补）。
- 若想让自动升级流水线真正走一遍「编译执行 + 自迭代」，需**新建**目标并走「创建为 backlog → 手动启动」流程；预计翻译器能对 lost_parallelism 类 finding 出 fork 提案（前提是修复 1 或走手动激活路径）。
- 本次诊断的副作用记录：`PUT /logs/level` debug 实验 + `POST /rsi/sessions/07f2df9f…/retry` 产生了一条 round 5（manual_retry）训练轮次记录（数据无害，与 round 4 指标一致）；日志级别已恢复 info；数据库已备份至 `/tmp/ouroflow-db-backup-1121.db`。
