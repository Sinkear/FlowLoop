## 1. 第一性原理：界面应该讲哪条故事

用户进来只该问三个问题：

> **我现在要为什么项目干活？这件事交给谁、按什么章法干？干完以后怎么变好？**

对应到实体：

| 用户的问题 | 实体 | 界面的回答 |
|---|---|---|
| 在哪儿干、验收标准是什么 | 项目 | 仓库、分支、验收策略、这个项目下的任务/定时任务 |
| 谁来干 | 小队 / Agent | 可复用的执行团队，或一个单干的 Agent |
| 按什么章法干 | 工作流 | 小队版本化的执行编排：节点、依赖、卡点、角色 |
| 现在什么在等我 | 工作台 | 待审批、待回答、失败、待批提案 |
| 干完以后怎么变好 | 复盘 → 发现 → 提案 → 新版本 | 一条从执行到改进的闭环 |
| 下次怎么复用 | 实践库 | 经过验证的项目/小队/工作流组合（“最佳实践”是徽章） |

一条主线：

```
项目 ──创建──▶ 任务 ──执行──▶ 运行记录
  │                │                 │
  │                └──── 复盘 ──▶ 发现 ──▶ 提案
  │                                       │
  └── 下一次任务 ◀── 新版本 ◀── 批准/发布 ┘
```

这条线上有四个“人出现的卡点”：待审批任务、待回答提问、待确认发现、待批提案。**工作台就是这四个卡点的统一收件箱**；其他页面都是这条线的透镜。

由此得到五条界面原则：

1. **用户不是来管理表的，是来推进工作的。** 每个页面必须回答“下一步做什么”，而不是“这里有哪些记录”。
2. **一个实体只有一个“家”，其他页面只做透镜。** 任务的家是任务详情；工作流的家是小队；复盘不是独立的家，它是任务/工作流/小队身上的一个 tab。
3. **深度不是问题，断头路才是。** 工作流放在小队下没问题，只要任务创建、任务详情、复盘、提案、命令面板都能链过去。
4. **命名是承诺。** 叫“工作流”就会让人期待拖拽 builder；叫“最佳实践”就会让人期待被验证过。名字先于功能，功能没到就不要先承诺。
5. **公共资源和私有资源必须显式。** Agent、小队是公共的；工作流是小队的；实践库包是只读的、可复制的。三者混在一起，用户就不知道“改这个会不会影响别人”。

## 2. 六条主张逐条评审

### 2.1 项目为首层：方向对，但“首层”不等于“唯一入口”

**你对的地方。** 数据上项目已经是归属：`goal.domain_id`、`schedule.domain_id`；非 human 的任务必须挂项目（`internal/service/goal.go:300-390`）。但界面完全没有把这条关系讲出来。用户看到的是一张全局任务板，卡片上连项目名都没有。

**要补的两个缺口：**

- **项目详情页。** 现在只有 `domains/page.tsx` 的列表 + 弹窗配置。项目需要自己的首页：概览、任务、定时任务、服务小队、设置。这样“项目下建任务/定时任务”才成立。
- **跨项目待办。** 人会被同时指派到多个项目。如果把待办完全藏进项目，用户就要挨个点开项目找事。所以首层应该是“工作台（跨项目待办）+ 项目（上下文）”，而不是“项目列表就是首页”。

**建议。**
- 根路径 `/` 改为工作台，不再 `redirect("/goals")`。
- 工作台顶部是“待我处理”，下面是“我的项目”和“最近活动”。
- 任务板增加项目筛选；任务卡显示项目名、小队、工作流版本、复盘状态。
- 项目详情页承载任务/定时任务/服务小队/设置。
- 项目不是硬租户：小队仍然可以服务多个项目，不要把项目做成隔离墙。

**顺带暴露的一个洞。** 定时任务表 `schedule`（`internal/store/schema.sql:585-600`）没有 `execution_mode`、没有工作流字段；daemon 触发的 goal 永远是默认 infer、无分析、无工作流。所以“项目下的定时任务”如果只是把现有页面搬过去，它仍然不参与优化闭环。这是数据模型问题，不是排版问题（见 §4）。

### 2.2 runtime + 机器合并：对，而且应该做成 master-detail

**数据层级很清楚：** `machine → runtime → agent`。机器是主机，运行时是 Agent 干活的“席位”，Agent 绑定在某个 runtime 上。

**现状的问题。** 两个平级页面，用户排障时要在“机器”和“运行时”之间来回跳；而真正想知道的是“这个 Agent 为什么跑不起来”。

**建议。**
- 一个“运行环境”页：左边机器列表，右边选中机器的详情；机器展开是运行时；运行时展开是绑定的 Agent。
- 每个层级显示健康状态和“影响面”：这台机器离线会影响 3 个 Agent、2 个小队；这个 runtime 没有模型；这个 Agent 没有可用 runtime。
- “添加机器”给一条可复制的安装命令；“添加运行时”就在机器详情里。
- 不要做成两个 tab。tab 会继续把两个概念当平级，master-detail 才能讲清“机器提供算力，运行时是席位”。

### 2.3 Agent 作为公共资源：模型已经是，缺的是“被谁用”

**模型现状。** `agent` 是全局表，绑定 `runtime_id`、model、system_prompt、env、mcp_servers、skills；通过 `squad_member` 被小队选中；也可以直接做 goal 的 assignee。

**但有两个容易讲错的点：**

- **“公共”不等于“可移植”。** Agent 仍然绑定 runtime。换机器/换运行时需要重新绑定。所以 Agent 卡片要显示 runtime 健康状态，否则“公共资源”会让用户以为复制一份就能到处跑。
- **角色是小队内的角色。** `squad_member.role` 是“这个 Agent 在这支小队里干什么”；同一个 Agent 可以在 A 队是 `reviewer`，在 B 队是 `go-dev`。不要把 role 画成 Agent 的属性。

**建议。**
- Agent 列表：模型、runtime 健康、所属小队、最近任务。
- Agent 详情：配置、被哪些小队使用、最近任务、克隆、删除保护。
- 小队成员选择器里支持“内联新建 Agent”，不要逼用户先跳去 Agent 页再回来。
- 明确“单干 Agent”路径：Agent 直接接任务时没有小队、也没有工作流；这条路径要视觉上区别于“小队按工作流执行”。

### 2.4 小队作为公共资源：模型已经是，问题是双轨关系

**模型现状。** `connection(squad_id, domain_id, provider, repo, events, webhook_path, secret)` 就是“项目 ↔ 小队”的多对多服务关系；一个小队可以接多个项目，一个项目也可以被多个小队服务。

**但同时还留着旧版“项目单指派”：** `domain.issue_assignee`、`issue_assignee_type`、`pull_assignee`。小队详情页把两者合并展示，用户看到的是两套关系。

**建议。**
- 把 `connection` 定为唯一的“服务关系”。项目详情显示“服务小队”，小队详情显示“服务的项目”。
- `domain.issue_assignee` / `pull_assignee` 逐步迁移成 connection 上的默认值，或者标为“旧版默认”，不要再让用户在两处配置。
- 小队不是组织架构，是“可复用的执行团队”。文案不要写成“部门/成员管理”。

**一个关键推论。** 小队的角色词汇表（`squad_role` / `squad_member.role`）是这支小队的“岗位契约”。工作流里的 `capability:<role>` 就是按这个契约解析的。这正是“工作流天然带小队色彩”的代码证据——也是第 5 条要讨论的核心。

### 2.5 工作流归小队：这是全文最重要的一条

#### 你的观察有代码证据

工作流节点可以写 `capability:<role>`。编译时，平台拿 **goal 自己的小队** 去解析这个角色（`internal/service/blueprint.go` 的 `resolveCapabilityTx`，约 3077-3123）；`squad:` 节点编译成该小队的 leader。也就是说：

- 同一份蓝本，交给 A 队和 B 队执行，节点会解析到不同的人；
- 交给一个“单干 Agent”的任务，带 capability 节点的蓝本会在编译时直接报错：`requires a squad-assigned goal`。

所以你说“蓝本基本是在给小队定制”，**在语义层面是对的**：它的节点含义依赖执行它的小队。

#### 但已批准的设计做了相反的选择

`docs/BLUEPRINT-PROPOSAL.md` §11.1（2026-11-18，用户已认可）写得很明确：

> “三个概念只在 goal 创建时相交（项目 × 小队 × 蓝本），**不构成硬层级**。”
>
> “**蓝本故意不绑定项目**：蓝本是流程模板，同一份可在任何项目下复用；项目归属发生在任务层。”
>
> “**任何一层换人都只影响解析结果，不影响蓝本结构**。”

`docs/design/DESIGN.md` 决策 8-1 也把“项目-小队-蓝本”称为三层模型，但同样没有给 blueprint 加 `squad_id`。

这不是实现漏了，而是一个**刻意的设计选择**：蓝本是跨队复用的流程模板，靠 capability 在 goal 的小队里晚绑定。你现在的提案，是把这个选择改成“蓝本是小队的 SOP”。两种模型都能自洽，但它们的代价不同。

#### 一个关键澄清：加 `squad_id` 不会自动改变执行

`resolveCapabilityTx` 现在拿的是 **goal 自己的小队**（`internal/service/blueprint.go:3077` 的调用参数是 `goalSquadID`）；对 agent-assigned goal，调用方会直接 fail-closed。也就是说：

- 如果只在 `blueprint` 上加 `squad_id`，把一个“A 队的工作流”钉到 B 队的 goal 上，角色仍然从 B 队解析。小队页会宣称“这是 A 队的工作流”，执行却按 B 队的人来——界面在撒谎。
- 要让“归属”成为事实，编译必须改成按 `blueprint.squad_id` 解析，并在钉住时硬校验 `goal.assignee_type='squad' AND goal.assignee_id=blueprint.squad_id`。**pin 为空是合法的（D2）；只有 pin 非空时才校验。** 否则 `squad_id` 只是一个文件夹。

另外，`internal/store/schema.sql:419` 的 `sub_goal.team_squad_id` 和 `docs/BLUEPRINT-PROPOSAL.md` §11.5 的“多小队蓝图”修复说明：跨队执行是**已发布的行为**，不是边角料。改成“一个小队所有”（已拍板 D1）必须新增 spec 校验器规则：禁止 `squad:<别队>`，禁止 `capability:` 节点解析到 owner 之外的小队；否则不变量只是文案。

#### 两种模型，选哪个？

| | 模型 A：你的方案（小队所有制） | 模型 B：现状（跨队流程模板） |
|---|---|---|
| 工作流的含义 | 这支小队的作业标准 | 一类任务的通用形状 |
| 提案由谁负责 | 小队 owner，责任清楚 | 全局，谁都能批，反而没人负责 |
| 指标分母 | 这支小队的执行 | 所有小队的执行混在一起 |
| 跨队复用 | 复制 / 实践库验证包 | 直接复用，晚绑定 |
| 角色词汇差异 | 天然一致 | 需要各队有相同 role 才能复用 |
| 版本演进 | 一队一版，A/B 清楚 | 一版多队，A/B 归因困难 |

**我建议选 A**，理由不是“用户想这么干”，而是：

1. **RSI 闭环需要一个 owner。** 提案批准、版本发布、指标变好，必须有人/有队负责。全局蓝本的“owner”是空的，提案区就成了公共留言板。
2. **工作流的有效性依赖这支小队。** 同一套节点，A 队跑得顺，B 队角色词汇不同、能力不同，未必跑得顺；把它们当成一份可共享的模板，等于假设两队可互换。
3. **“实践库”正好承担跨队复用的角色。** 复用应该是“复制一份，变成你的”，而不是“大家改同一份”。这也符合实践库包“只读、可复制”的定位。
4. **UI 上终于能说人话。** “我们队的工作流”比“全局蓝本库里的第 7 号”更像一个产品。

**但选 A 必须付五笔账：**

- **历史蓝本不处理。** 已拍板 D5：不迁移、不认领；旧工作流 `squad_id=''` 冻结为“历史工作流”，只读、不可被新任务选中；已有 pin 的任务继续按旧解析跑完。新数据必须带 owner。
- **执行解析与 spec 校验要跟着归属走。** 编译要从“按 goal 的小队解析”改成“按工作流的小队解析”，并在钉住时校验 `goal.assignee_id == blueprint.squad_id`；同时新增 spec 规则，禁止 `squad:<别队>` 和指向别队的 `capability:`。否则 `squad_id` 只是文件夹，界面照样撒谎。
- **单 Agent 任务不能钉工作流；小队任务可以显式不使用工作流。** 已拍板 D2：工作流是小队的 SOP，但不是每件活都值得按 SOP 走。默认按“小队默认工作流”执行，允许选“不使用工作流，自动拆解”。规则要同时写进表单和校验，不能只在 UI 上给选项。
- **跨队复用变成复制。** 版本会分叉，这是接受的代价；想共享就用实践库验证包，而不是共享可变实体。
- **分析与提案的聚合要改。** 现在 `training_session` 只挂 goal，没有 workflow/squad；`infer_shape` 的收敛只按 domain 查最近 3 条，不区分 squad。工作流归队之后，这些查询都要按 (domain, squad) 或 workflow 重做。

**所以，第 5 条不是“把蓝本页搬到小队下”的导航调整，而是一次实体归属变更。** 如果只加 `squad_id`、不改编译解析和 spec 校验，界面同样会撒谎：小队页说“这是我们的工作流”，编译却按执行它的小队解析角色。只改导航更糟——小队下的“工作流”其实还是全局的，另一个小队也能改。

#### 关于“finding 确认后才展示提案”：前提不成立

你说“训练页 finding 确认后才会在蓝本的优化提案里面展示提案”。代码不是这样：

- 分析完成时，`internal/service/rsi_analyze.go:225` 会自动调用 `draftAutoProposals`，提案已经生成。
- `web/components/training/findings.tsx:81` 的“确认”按钮只改 `rsi_finding.status`，不创建提案，也不跳转。
- 翻译器只处理**钉住且已编译**的工作流任务，每次最多 4 条；infer 任务直接跳过（`internal/service/rsi_translate.go`）。

所以你感受到的“跨页面体验不好”是真的，但原因不是“确认门槛”，而是：

1. 提案生成是自动的，UI 没有告诉用户“已经生成了”；
2. infer 任务根本没有提案，UI 也没有解释“为什么没有”；
3. 发现和提案分在两个页面，没有互相链接。

**建议的修法不是加门槛，而是把因果摆在一屏：**

- 复盘详情右侧固定一个“已生成的提案”面板；发现卡上直接显示“关联提案”或“暂无可自动生成的提案”。
- 确认发现后，如果该任务符合条件且尚无提案，给一个“基于此发现创建提案”的动作；如果不符合，明确说“本次任务未钉住工作流，无法自动翻译；可先把这次执行固化成工作流”。
- 工作流的提案 tab 里，每条提案显示来源任务/发现；任务详情的复盘卡显示“N 个发现 → M 条提案”。
- 不要用“确认发现”来隐藏提案。确认是“我同意这个诊断”，提案是“我建议这么改”；两者是不同动作，绑在一起只会多一步。

#### 分析不要整体搬进小队

你希望“分析在小队下体现”，这个方向对，但不能只放小队：

- **任务详情**要有“复盘”tab：这次执行发生了什么，是任务上下文的一部分；
- **工作流详情**要有“复盘”tab：这个工作流的历次执行、版本对比；
- **小队详情**要有“复盘”tab：这支小队所有工作流的汇总。

三个透镜，同一份数据。这样单 Agent 任务也有地方看复盘，跨小队比较也有地方看。把分析只放小队，会让“任务详情”失去闭环，也会让单干任务无家可归。

#### 入口变深：用链接解决，不要用扁平化解决

工作流放在小队下，入口确实变深。正确的解法是：

- 工作流有稳定 URL，任务创建、任务详情、复盘、提案、命令面板都能直接跳；
- 任务创建时按“项目 → 小队 → 工作流”过滤，不要给全局蓝本下拉；
- 工作流详情有“用于新任务”按钮，直接带着 squad + workflow 预填创建表单；
- 命令面板（⌘K）能搜到工作流，不需要先点小队。

这样“深”只体现在层级上，不体现在找路上。

#### 改名之前，先解决“工作流”这个名字的承诺

现在的“新建蓝本”页是 7 份模板 + 原始 JSON 编辑器（`web/app/blueprints/new/page.tsx`），没有可视化编排器。叫“蓝本”时，用户还能接受“这是个技术 spec”；叫“工作流”时，用户会期待拖拽 builder。**改名会提高期望，而当前功能接不住。**

最低限度要先有这三个创建路径，再改名：

1. **从实践库开始**（现成的工作流包）；
2. **从已完成任务固化**（把一次跑顺的执行变成 draft）；
3. **从空白创建**（结构化表单，JSON 收进“高级”）。

否则“工作流”三个字会变成负资产。

### 2.6 模板改实践库：容器名先落地，“最佳实践”留给验证包

**现状。** `templates` 从 GitCode 模板仓库拉取，`kind = project-template | squad-template`；spec 支持 `repo.create / domain / team(agents+squad) / goals / schedules`。应用后创建实体，没有 workflow 类型，也没有“已验证/来源/版本”的元数据。

**你的想法。** 改名最佳实践，未来导入项目、小队、工作流；实现可以先空着，样式先出。

**已拍板 D4：容器叫“实践库”，不叫“最佳实践”。** “最佳实践”是页面里的一个验证徽章，不是导航名。这样既解决“模板这个词太弱”的问题，又不用在第一批内容还不可靠时透支“最佳”的承诺。

**实践库的规则：**

- 徽章分级：**官方验证 / 社区分享 / 未验证**；只有官方验证可以显示“最佳实践”。
- 包模型至少要有：来源、版本、适用范围、包含内容（项目/小队/工作流/Agent/技能）、前置要求（runtime/model）、验证时间、应用记录。
- 空状态不要放一排假卡片。先拿现有的 1-2 个模板做真包，标“官方起步包”；“导入工作流”可以标“即将支持”，但要解释为什么现在不能点。
- “应用”要能预览将创建什么、覆盖哪些名字、绑定哪个 runtime；“应用后是你自己的副本”，这句话要写在按钮旁边。
- 导航、页头、文案统一用“实践库”；旧 `/templates` 路由可以保留，避免打断书签，但标签要改。

**为什么不是直接叫最佳实践。** “模板”是一个诚实的词——它只承诺“这是一个可套用的起点”。“最佳实践”承诺“这是被验证过的好东西”。容器名先落地，徽章慢慢升级；等有 3 个官方验证包，再把“最佳实践”作为主标题也不迟。

### 3.5 迁移：不处理历史，只保证新数据

D5 之后，迁移不做“猜归属/认领”，只做三件事：加历史桶、挡住新写入、把唯一约束改成按队。

1. **加 `squad_id TEXT NOT NULL DEFAULT ''` 作为历史桶**，不建 FK。现库只支持 `ADD COLUMN ... DEFAULT`（`internal/store/store.go:190-194`）；`''` 就是“历史无主”，不是待办。
2. **不迁移、不认领。** 旧的全局蓝本全部留在 `''`；不做确定性回填，不做认领 UI。历史工作流只读，不能发布新版本，不能被新任务选中。
3. **新写入必须带 owner。** `Create` 的 `squadID` 参数、HTTP handler、chat intake 都要非空；旧代码路径保留 `squad_id=''` 的读兼容。
4. **存量任务不转换。** 已有的 agent+pin 任务、跨队 pin 的任务继续按旧解析跑完；只禁止新任务产生这些组合。不要为了“整齐”去改历史 goal。
5. **重建唯一约束。** `UNIQUE(name)` 是 inline（`schema.sql:253`），`ALTER` 改不了；重建表改成 `UNIQUE(squad_id, name)`，复制旧行时保持 `squad_id=''`，所以旧名字仍在同一个历史桶里，不会互相冲突。**不建 FK**：`''` 历史桶会让真实 FK 失败，靠服务层 + 删除守卫。
6. **编译走双轨。** `blueprint.squad_id != ''` → 按 owner 解析并校验 goal 小队；`== ''` → 仅对已存在的 pin 走旧 fallback（goalSquadID）。新任务在创建时就被挡住，不会进入这个分支。
7. **自动固化改归属。** `DraftFromGoalExecution` 写入 goal 的 squad；Agent 单干任务不再自动固化。去重键从全局 `name` 改为 `(squad_id, signature)`，`rsi.max_auto_rounds` 也按 squad 计数——否则一个形状会在每个队各固化一次。
8. **复盘聚合加维度。** `training_session` 冗余 `squad_id` / `blueprint_id` 快照；旧会话的 `squad_id=''` 归历史桶，不回填。`rsi_round.round_no` 的“per domain”改成 per (squad, workflow)。
9. **定时任务补字段并钉版本**（D3）。`blueprint_version_id`、`analysis_enabled`、capture/sample/budget；保存时 pin，发布后提示落后。
10. **代码面一起改。** `Create` 加 `squadID`；select/list/handler/`web/lib/api.ts` 加过滤；`UpdateDraft`/`Publish` 在已有 published 后禁止改 squad；`squad.go:428` 删除守卫加“有工作流不能删”；chat intake 增加小队字段。

**代价：** 旧工作流永远留在历史区，不能继续演进；新任务不能再用它们。这是 D5 换来的简化——不做回填/认领，但也不能假装它们有 owner。

### 4.3 工作台：四个卡点的收件箱

首屏顺序：

1. **待我处理**：待审批任务、待回答提问、失败/阻塞、待批提案。每条显示项目、小队、等了多久、下一步按钮。
2. **进行中**：正在跑的任务，显示当前节点、谁在干、预计卡点。
3. **最近完成**：终态任务 + 复盘状态（已生成 / 未开启 / 已跳过）+ “查看复盘”。
4. **定时任务**：未来 24 小时将触发的；上次结果。
5. **我的项目**：项目卡片（活跃任务、待审、服务小队）。
6. **对话**：最近对话/助手入口。

空状态（第一次用）：

> 还没有项目。
> 1. 连接一台机器（运行环境）
> 2. 创建第一个项目
> 3. 从实践库导入一支小队，或自己建一支
>
> [连接机器] [创建项目]

不要一上来给 15 个入口。先给三步。

### 4.4 项目详情：项目终于有“家”

- **头部**：项目名、仓库/分支、验收策略、服务小队；`新建任务` / `新建定时任务`。
- **概览**：活跃任务、待审、本周完成、成本、下一次定时触发、最近活动。
- **任务**：看板/列表，默认本项目；支持按状态、小队、复盘状态筛。
- **定时任务**：cron、下次触发、上次结果、**工作流**、**复盘开关**；新建/编辑。
- **小队**：服务本项目的 squad 列表 + connection 配置；设为默认小队。
- **设置**：仓库、分支、验收级别、issue/pull 指派、webhook。

项目页要回答一句话：“这个项目现在有哪些活、由谁干、卡在哪。”

### 4.5 小队详情：团队 + 工作流 + 复盘

- **头部**：leader、成员数、服务项目、工作流数；`新建工作流` / `添加成员`。
- **概览**：待处理（待批提案、失败复盘）、最近执行、容量/负载。
- **成员**：Agent + human，队内角色；内联新建 Agent；角色词汇表入口。
- **工作流**：卡片列表（名称、最新发布版本、待批提案数、最近使用、关键路径趋势）；空状态给三个创建路径。
- **复盘**：这支小队所有工作流的执行复盘；按工作流/时间筛。
- **接入**：connection（仓库、事件、webhook）+ 服务项目；解释“这是项目 ↔ 小队的服务关系”。
- **设置**：名称、说明书、leader、归档。

**移除现在的“编排摘要”tab。** `SquadWorkflows` 是最近 10 个 goal 的执行图摘要，不是工作流列表；放在概览里做“最近执行”小部件即可，别和“工作流”混淆。

### 4.6 工作流详情：小队的作业标准

- **头部**：所属小队、最新发布版本、待批提案；`用于新任务`。
- **概览**：规范图、节点/角色、适用场景、最近指标（执行次数、成功率、关键路径趋势）。
- **版本**：时间线；diff；发布/退役；当前版本被哪些任务使用。
- **提案**：待批/已批/已拒；每条显示来源任务/发现、预期指标、diff；批准 → 生成 draft → 显式发布；下一轮 A/B。
- **复盘**：用过这个工作流的任务复盘；按版本对比。
- **设置**：名称、描述、归属小队（迁移期可见）、归档。

空状态（小队还没有工作流）：

> 这支小队还没有工作流。
> - **从实践库开始**：拿一个验证过的包，改成你们的。
> - **从已完成任务固化**：把一次跑顺的执行变成草稿。
> - **从空白创建**：自己排节点（高级）。

**“用于新任务”** 是关键按钮：带着 squad + workflow 跳到创建表单，用户不用再选一遍。

### 4.7 任务详情：一次工作的全生命周期

- **头部**：项目、小队、工作流版本、状态、attention。
- **概览**：目标、验收、成本、当前节点、谁在干、卡点。
- **执行图**：计划 vs 实际（工作流节点 vs 实际 run/sub_goal）；关键路径、并行、返工。
- **复盘**：复盘状态（已生成/未开启/已跳过/失败）、指标、发现、提案、CTA。
- **变更**：commit、merge、验证结果。

**终态卡片**（解决你第 5 条）：

> 复盘已生成：3 个发现，2 条提案。
> [查看复盘] [查看提案]

如果没开复盘：

> 本次未开启复盘。
> 适合一次性/探索性任务；不会产生优化提案。
> [为下一次开启]

如果是自动拆解（单干，或小队任务显式不用工作流）：

> 本次没有使用工作流，发现不会自动转成提案。
> 如果这类任务会反复出现，可以把这次执行固化成工作流。
> [固化为工作流]

### 4.8 新建任务：默认用工作流，但允许显式不用

D2 之后，执行方式不是“工作流 vs 自动拆解”的二选一，而是**“默认用工作流，可手动关掉”**：

```
执行方式
  交给小队时：
  (•) 使用小队的工作流（默认）
      [选择工作流 ▾]   默认选中「小队默认工作流」
  ( ) 不使用工作流，自动拆解
      适合一次性/探索性任务；跑顺了可以固化成工作流

  交给 Agent（单干）时：
  总是自动拆解，无工作流选项。

复盘
  [x] 执行后生成复盘（推荐）
      只分析这次执行的过程，不会训练模型。
      绑定工作流的任务，部分发现可转成该工作流的优化提案；
      自动拆解的任务没有提案，但可以固化成工作流。
      [ ] 高级：内容采集 / 预算 / 采样率
```

**“自动拆解”到底是什么意思？**

不是平台在任务开始前生成一张 DAG。是任务开始后，负责人 Agent 读完目标，自己决定拆成几个 work item、每个交给谁、谁等谁，然后用 `ouroflow subgoal create` 逐个创建。执行中它可以继续拆、改派、加依赖；平台只记录它实际拆出来的结构，任务完成后复盘分析的就是这张“事后长出来”的图。单干时它通常把子任务派给自己；小队任务里派给队友。

用工作流则相反：pin 的版本在 Activate 时由平台一次性编译成固定 `sub_goal` 行，拓扑和顺序由平台保证；负责人只做监控/集成/异常，`subgoal create` 会被平台拒绝（除非 spec 里显式放了 `spawn` 节点，那是有边界的运行时派活）。一个是“现场工头派活”，一个是“按图纸施工”。

**默认值解析顺序：** `squad.default_workflow_id` → 该小队最近发布的 published 版本 → 都没有则自动拆解。默认值必须显示在表单上（不是隐形），用户改过之后要记住这次选择，不要下次又弹回默认。

**校验规则（与 UI 同源）：**

- 选 Agent：`blueprint_version_id` 必须为空；
- 选小队 + 使用工作流：pin 非空，且 workflow 属于该小队；
- 选小队 + 不使用工作流：pin 为空，合法；
- 任何时候都不允许“pin 了别队的工作流”。

如果你保留“训练工作流”这个词，小字至少要写清三件事：**(1) 不会训练模型；(2) 分析的是这次执行图；(3) 只有钉住工作流的任务才会产出提案，自动拆解的任务要先固化。** 否则用户会以为平台在微调模型。

表单顺序：

1. **描述**：标题、描述；项目默认当前项目。
2. **交给谁**：小队 / Agent（单干）；项目必填。
3. **怎么干**：默认“使用小队工作流”，可切“不使用工作流”；工作流按小队过滤；该队没有工作流时给“从实践库创建”/“先自动拆解”。
4. **复盘**：开/关；解释清楚“复盘不等于训练模型”。
5. **验收**：跟随项目 / 人工验收 / 自动验收；高级。
6. **Hooks**：高级折叠。

右侧固定一个摘要：项目 / 小队 / 工作流 / 复盘 / 预算。提交前就能一眼看懂“这活怎么干”。

**定时任务复用同一套字段**，再加 cron/时区。不要再让定时任务成为“没有工作流、没有复盘”的特例。

### 4.9 复盘详情：一次执行的镜子

- **头部**：任务、项目、小队、工作流版本；一句话“复盘是一次执行的镜子，不是小队评分”。
- **概览**：节点数、关键路径、并行加速、瓶颈分类、成本。
- **发现**：严重度/置信度/证据/建议；确认/忽略；关联提案或“生成提案”。
- **工作流**：计划 vs 实际；节点级差异。
- **洞察**：重复模式、跨次趋势。

**发现与提案并排**，不要一个在上一个在下、中间隔一个页面。用户确认发现时，右侧就能看到“这条发现有没有变成提案”。

### 4.10 运行环境：一页讲清“为什么跑不起来”

- 左：机器列表（在线/离线、最后心跳、OS、运行时数）。
- 右：选中机器 → 运行时列表 → 每个运行时绑定的 Agent。
- 顶部健康摘要：离线机器 N、无模型运行时 N、未绑定 Agent N。
- 操作：添加机器（复制安装命令）、添加运行时、重启/探测、查看日志。
- 影响面：点一个离线机器，显示“会影响 3 个 Agent、2 支小队”。

不要做两个 tab。tab 是“并列”，master-detail 是“层级”。

### 4.11 Agent 库

- 列表：名称、模型、runtime 健康、所属小队、最近任务。
- 详情：system prompt、env、MCP、技能、runtime 绑定；被哪些小队使用；最近任务；克隆；删除保护（被小队/任务引用时不能删）。
- 创建：全局入口 + 小队成员选择器内联创建；后者自动带上“队内角色”。
- 文案：Agent 是公共资源，但绑定 runtime；换机器要重新绑定。

### 4.12 实践库

**已拍板 D4：容器叫实践库。** “最佳实践”是徽章，不是导航名；页面标题写“实践库”，筛选器里可以有“最佳实践（官方验证）”。

- 卡片：名称、来源、验证状态、包含内容、前置要求、使用次数、最后验证时间。
- 详情：树形预览（项目/小队/工作流/Agent/技能）；应用向导：选项目/小队 → 映射 runtime/model → 改名 → 预览 → 应用。
- 应用后：明确“这是你的副本，改它不会影响源包”。
- 空状态：1-2 个真实包 + “导入工作流（即将支持）”的解释；不要假卡片。
- 如果暂时没有验证包：页面顶部写“最佳实践徽章还在筛选中”；不要给未验证内容打这个标。

### 4.13 排版与密度

入口少了，不等于内容可以摊平。恰恰相反，少入口要求每个页面承担更多、层次更清楚。

```
┌─ sidebar 240 ─┬─ main ───────────────────────────────────┐
│ 工作台        │ 项目 / acme-web                 [+ 新建]  │
│ 项目          │ 仓库 main · 人工验收 · 2 支服务小队        │
│   全部项目    │ ┌ 概览 ─ 任务 ─ 定时任务 ─ 小队 ─ 设置 ┐  │
│ 小队          │ ├──────────────────────────────────────┤  │
│ 资源          │ │ 页面内容                             │  │
│    Agent      │ │                                      │  │
│    实践库     │ │                                      │  │
│ 运行环境      │ │                                      │  │
│               │ │                                      │  │
│ 日志   设置   │ └──────────────────────────────────────┘  │
└───────────────┴───────────────────────────────────────────┘
```

规则：

- **侧栏 240px，可折叠到 64px。** 项目只列最近 5 个 + “全部项目”，不要把项目做成第二棵树。嵌套最多两级（大队下的小队？不做）。
- **页头最多三行：** 面包屑（项目 / acme-web）→ 标题 + 唯一主按钮 → 一行元信息（仓库、验收、服务小队）。不要页头放五个按钮。
- **一个页面一个主按钮。** 次要动作收进“更多”。工作台的“处理”是按钮，不是整张卡片可点但看不出能点。
- **tab 最多 6 个。** 超过就合并或收进“更多”；tab 名称用名词（概览/任务/复盘），不要动词短语。
- **实体用卡片，运行记录用表格。** 3 个字段不要上表格；日志/运行列表不要做卡片墙。
- **空状态 = 一句解释 + 一个动作。** 禁止“暂无数据”四个字。
- **密度：** 8px 网格，列表行高 32–36px；正文不小于 14px，辅助信息不小于 12px；不要用 11px 灰字承载关键信息。
- **响应式：** <1024px 折叠侧栏；<768px tab 横向滚动，页头按钮收进“更多”。不做手机优先，但不能在窄窗口爆版。
- **视觉层级靠留白和字重，不靠颜色堆叠。** 状态色只用于状态（成功/警告/失败/等待），不要给每个实体一个色。

## 5. 跨页面闭环：一条链，四个卡点

| 步骤 | 页面 | 用户看到 | 动作 | 去向 |
|---|---|---|---|---|
| 1 | 工作台 | 待我处理 / 我的项目 | 点项目 | 项目详情 |
| 2 | 项目详情 | 任务、定时任务、服务小队 | 新建任务 | 任务表单（预填项目） |
| 3 | 任务表单 | 小队 → 工作流（默认，可不用）→ 复盘 | 创建 | 任务详情 |
| 4 | 任务详情 | 执行图、当前节点、卡点 | 等完成 / 审批 | 终态卡片 |
| 5 | 任务详情 | “复盘已生成：3 发现 / 2 提案” | 查看复盘 | 复盘详情 |
| 6 | 复盘详情 | 发现 + 已生成提案并排 | 确认发现 / 生成提案 | 提案详情 |
| 7 | 提案详情 | diff、预期指标、来源任务 | 批准 | 新 draft 版本 |
| 8 | 工作流详情 | 版本时间线、提案 | 发布 / 用于新任务 | 任务表单（预填） |
| 9 | 下一次任务 | “v4 · 来自 3 次复盘” | 创建 | 闭环 |

**链接规则：**

- 任务卡/任务详情永远显示：项目、小队、工作流版本、复盘状态。
- 每条提案永远显示：来源任务、来源发现、目标工作流、base 版本。
- 每个版本永远显示：被哪些任务使用、由哪条提案产生。
- 每个终态永远有下一步：审批/复盘/重跑/归档。
- 每个空状态永远有一个动作，不是一句“暂无数据”。

这五条做到，入口深不深就不重要了——用户永远在一条有来有回的链上。

## 6. 命名与文案

### 6.1 术语表

| 现名 | 建议 | 代码 | 说明 / 不要叫 |
|---|---|---|---|
| 蓝本 | **工作流**（小队工作流） | `blueprint` | 不要再叫“蓝本”；也不要叫“通用工作流/自动化”，会和 DESIGN.md 的非目标冲突 |
| 训练分析 / 训练 | **复盘** | `training` / `rsi` | “训练”暗示 ML 微调，实际是执行分析；高级里可保留“分析” |
| 模板 | **实践库** | `template` | 容器名；“最佳实践”只作为官方验证徽章 |
| 智能体 | **Agent**（智能体） | `agent` | 主 UI 用 Agent，首次出现括注“智能体”；不要混用 |
| 项目 / 域 | **项目** | `domain` | UI 统一项目；代码不改 |
| 任务 / goal | **任务** | `goal` | UI 统一任务 |
| 小队 / squad | **小队** | `squad` | 不要叫“部门/团队管理” |
| 运行时 / 机器 | **运行环境**（机器 / 运行时） | `runtime` / `machine` | 一级导航叫运行环境；子概念保留 |
| 提案 | **优化提案** | `blueprint_proposal` | 紧凑处用“提案” |
| 发现 | **复盘发现** | `rsi_finding` | 不要用 finding 这种黑话做主标签 |
| HITL / HOOTL | **人工验收 / 自动验收** | `category` | 代码值保留；主 UI 不要露缩写 |
| 卡点 | **卡点** | `gate` | 保留，这是产品的好词 |

### 6.2 文案示例

- 工作台：**“需要你拍板的事，都在这里。”**
- 项目：**“项目是任务的家：仓库、验收标准，以及由哪些小队来干。”**
- 小队：**“小队是可复用的执行团队。工作流是这支小队的作业标准。”**
- 工作流：**“把这类任务拆成节点、依赖和卡点。发布后，新任务可以按它执行。”**
- 复盘：**“这次执行在哪里等、哪里返工、哪里串行。”**
- 提案：**“一条基于复盘的改进建议。批准后生成新版本，不会自动发布。”**
- 实践库：**“经过验证的项目、小队和工作流组合。应用后是你自己的副本。”**
- 最佳实践徽章：**“官方验证过，可以直接起步。”**
- 运行环境：**“机器提供算力，运行时是 Agent 干活的席位。”**

**文案纪律：**

- 每个页面头部一句话说“这是什么、为什么我要关心”。
- 空状态：一个解释 + 一个动作。
- 不要在主 UI 露 JSON、UUID、HITL/HOOTL、infer/train。
- 说清后果：“停用这个 runtime 会影响 3 个 Agent”，比“确认停用？”有用。
- 不要用“训练”描述分析；不要用“最佳”描述未验证内容。

### 6.3 三个命名风险

1. **“工作流”与“不做通用工作流”的冲突。** `DESIGN.md` §0 明确写“不做通用工作流”。你要把蓝本改叫工作流，必须同时把这句话改写成“不做通用自动化工作流；工作流是小队的执行编排”。否则团队会沿着“工作流”这个词滑向 n8n/Zapier 的产品形态。
2. **“实践库”已拍板，剩下的风险是徽章滥用。** 没有验证机制之前，不要给包打“最佳实践”；先用“官方起步包 / 社区分享 / 未验证”三档。
3. **“复盘”比“训练”准确。** 训练暗示模型会变；实际变的是工作流。这个改名会直接降低用户的误解成本。

## 7. 数据模型改动清单

> 这一节是给工程的，不是给 UI 的。原则：**加历史桶、挡新写入、重建约束；不做回填**；不要一次性重命名 Go/DB 标识符。
>
> 审计后补两条硬约束：**归属必须同时改执行解析**（否则只是文件夹）；**迁移不能直接加 `NOT NULL`**（现库只支持 `ADD COLUMN ... DEFAULT`，inline UNIQUE 要重建表）。

| 改动 | 表/字段 | 目的 | 风险 |
|---|---|---|---|
| 工作流归属 | `blueprint.squad_id TEXT NOT NULL DEFAULT ''` 历史桶；**不迁移/不认领**；新写入必须非空；重建约束，不加 FK | 新工作流有 owner；旧的不假装有 | 旧数据只能只读；靠服务层守卫 |
| 名称唯一性 | 重建表：`UNIQUE(name)` → `UNIQUE(squad_id,name)`，复制旧行时保持 `''` | 不同队可同名 | inline UNIQUE 只能重建 |
| 执行解析 | owner 非空 → 按 `blueprint.squad_id` 解析并校验 goal 小队；owner 为空 → 仅旧 pin 走 fallback | 让归属成为事实，又不阻塞历史 | 新任务在创建时挡住 |
| spec 校验 | 禁止 `squad:<别队>`、指向别队的 `capability:` | 不变量可执行 | 已有多小队 spec 会被拒 |
| 任务校验 | pin 可选；pin 非空 ⇒ assignee 是 squad 且 owner 匹配；Agent 任务 pin 为空 | 消灭新非法组合，同时保留 D2 的 opt-out | 存量 agent+pin 不迁移，继续跑完 |
| 默认工作流 | `squad.default_workflow_id`（指向 workflow，不是 version；创建任务时解析 latest published 并 pin）+ 创建/更新校验 | “默认使用工作流”有确定来源 | 需 UI 维护；删工作流时清空 |
| 更新/发布守卫 | 有 published 版本后 squad 不可变 | 历史 pin 不悄悄换角色 | 需要 UI 说明 |
| 小队删除守卫 | `squad.go:428` 增加“有工作流不能删” | 避免裸 SQL 错误 | 需新增错误码 |
| 创建/列表 plumbing | `Create` 加 `squadID`；select/list/handler/api 加过滤 | 新模型贯通 | 约 16 处测试调用 |
| 执行/复盘拆分 | `execution_mode` → `plan_mode`（infer/workflow）+ `analysis_enabled` | “训练”不再 overloaded | 迁移 + API 兼容 |
| 定时任务 | `blueprint_version_id` / `execution_mode` / capture / sample / budget；保存时钉版本 | 定时任务进入闭环 | 落后版本要提示 |
| 复盘聚合 | `training_session` 冗余 `squad_id` / `blueprint_id` | 历史不悬空 | 旧会话归历史桶，不回填 |
| 固化 | 写 `squad_id`；`(squad_id, signature)` 去重；per-squad cap | 草稿有家 | 单干不再固化 |
| 收敛 | `infer_shape` 按 `(domain_id, squad_id)` 查，加索引 | 队间不混 | 空 squad 归“单干桶” |
| 提案 | 不改表；补来源链接 | 提案有主 | UI 为主 |
| 实践包 | 实践库 manifest（JSON/Git 都可），记录来源/验证/要求 | 验证徽章可信 | 可后置 |

**版本策略（定时任务）：** **已拍板 D3：保存时钉住版本，发布后提示“落后 N 版”并提供一键更新。** 不要每次触发取最新：同一 schedule 每周拓扑不同，复盘不可比，`content_hash` 漂移保护也失去意义。pin 的代价是优化不会自动生效，所以 UI 必须把“落后”做成可见的、一键的动作，而不是让用户自己去发现。

**迁移顺序：**

1. 加历史桶列 + 双读；
2. 代码 plumbing + 编译解析 + spec 校验（先 warning）；
3. 任务/定时任务/下一轮的钉住校验；
4. 重建表，收紧 `UNIQUE(squad_id,name)`，不加 FK；
5. 改自动固化/收敛/复盘聚合；
6. 补定时任务字段；
7. 隐藏旧入口，历史工作流只读。

**一个容易忽略的耦合：** `blueprint.name` 的全局唯一目前是自动固化去重的 de-facto 命名空间（`blueprint.go:3666` 注释：“blueprint.name UNIQUE ⇒ same shape does not double-draft”）。改成 per-squad 后，`rsi.max_auto_rounds` 不再全局约束草稿数量；必须同时把去重键和配额都改成 per-squad，否则草稿会成倍增长。

## 8. 实施顺序与“不做什么”

### 8.1 四个阶段

| 阶段 | 内容 | 数据变更 | 用户看到 |
|---|---|---|---|
| **A. 叙事骨架** | 6 项导航、工作台、项目详情、任务板项目筛选/项目名、任务表单直接暴露执行方式/复盘（当前默认自动拆解；小队默认工作流随 B 落地）、实践库改名（标签/徽章样式）、跨页链接、运行环境合并 | 无（全部读现有字段） | 进来知道先干什么；项目有上下文；任务能跳复盘；模板不再叫模板 |
| **B. 归属变更** | 历史桶列 + 不迁移/冻结 + 重建约束、编译按 owner 解析、spec 校验、pin 可选+owner 匹配校验、小队默认工作流、工作流迁到小队、改名、提案/复盘聚合 | 有 | “我们队的工作流”成立，且执行真的按 owner 解析 |
| **C. 闭环补全** | 定时任务工作流/复盘、发现→提案动作、任务终态卡片、复盘按工作流聚合 | 有 | 定时任务也参与优化；确认发现能看到结果 |
| **D. 实践与编辑器** | 实践包（含工作流）、验证徽章、结构化节点编辑、应用向导 | 可后置 | 工作流不再只能写 JSON |

**A 阶段不要改名“蓝本”。** 先做叙事骨架，等 B 阶段有 `squad_id` 再改。半改名（页面叫工作流、数据是全局）比不改更伤。

**实施状态（2026-11-25，Phase A/B 已落地）**：

- **A 叙事骨架**：`/` 工作台、`/projects` + `/projects/[id]`、任务板项目筛选与项目名、`/goals/new` 直表单 + 右侧 `CreateTree`、`/infra` 机器/运行时 master-detail、`/training` 复盘改名与项目/小队上下文、小队详情 6 tab、`/templates` 实践库（空态 + 示例，不再自动拉 GitCode）。旧 `/domains`、`/runtimes`、`/machines` 跳转；桌面 240px 侧栏、移动 48px 顶栏。
- **B 归属变更**：`blueprint.squad_id` + `UNIQUE(squad_id,name)`；`squad.default_workflow_id`；旧表专用重建迁移（`squad_id=''` 历史桶、只读、不迁移/不认领）；编译按 owner 解析；pin 可空、非空才校验 owner；单 Agent 禁 pin；spec 禁止跨队 `squad:`/`capability:`；自动固化写 owner；复盘收敛按 squad；HTTP/daemon 创建工作流必须带小队；`/workflows/{page,new,[id]}` 取代 `/blueprints`，导航中工作流回小队。
- **验证**：`go test ./...`、`cd web && npx tsc --noEmit`、`npm run build` 均通过；隔离 DB + 浏览器检查了默认 pin、opt-out、跨队/单 Agent 拒绝、实践库空态与移动布局。
- **未做（C/D）**：定时任务仍无 `blueprint_version_id`/复盘字段；发现→提案仍是分析时自动生成、UI 未提供手动生成；工作流仍只能写 JSON，没有结构化节点编辑器；实践库尚无真实来源与导入向导。

### 8.2 明确不做

- 不要为了减少导航而新增第 7 个“工作流”一级入口。工作流的家是小队。
- 不要用“确认发现”来隐藏提案；提案已经自动生成，隐藏只会让用户以为没发生。
- 不要把未验证包打成“最佳实践”；容器叫实践库，徽章才叫最佳实践。
- 不要把项目做成硬租户；小队必须能服务多项目。
- 不要在第一版重命名所有 Go/DB 标识符；UI 标签先行。
- 不要删掉全局任务板；把它变成工作台的一个视图，保留跨项目视角。
- 不要让“工作流”变成通用自动化 builder；先改 DESIGN.md 的非目标表述。

### 8.3 最大的三个风险

1. **历史工作流会被冻结。** 旧的无主工作流不能再被新任务选中，只能读；这是 D5 的明确代价。先只读兼容，不要把旧任务跑挂。
2. **改名快于功能。** “工作流”+ JSON 编辑器 = 期望落差。先补三个创建路径，再改名。
3. **分析搬家导致任务详情空心化。** 复盘只放小队，任务详情就失去闭环；单干任务也无家可归。三个透镜都要保留。
