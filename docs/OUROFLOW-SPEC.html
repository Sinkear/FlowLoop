第一篇 · 项目全貌：产品、架构、运行与运维

1产品定位与闭环

OuroFlow 是「AI 干活的流水线操作系统」。它把 agent 从一次性的对话框里拎出来，放进一条可触发、可验证、可卡点、可交付的自动流水线：平台管「活怎么流」，人只管「门什么时候开」。一句话概括分工——系统管活，人管门。当前版本 v0.0.1-beta.1，定位是单机、单用户的个人开发者基础设施，架构上焊死单用户，不做多租户。

维度定义
为谁做一个人维护多个仓库/项目的开发者：希望下班前把任务丢进去，第二天看验收结果，而不是整晚盯着 agent 聊天。
卖什么把 agent 从「互动工具」升级为「可调度、可审计的执行设施」：定时触发、无人执行、完成记账、人工出现在关键卡点、批准后合入并汇报。
不做什么不做执行引擎（真正干活的是各家 agent CLI）；不做「无人工全自动」（卡点是产品的一部分）；不做通用工作流编排（蓝图面向软件任务）；暂不做多用户与云端多租户。
差异化卡点是第一公民：卡点可声明、可挂状态转换、可统计（gate_decision），并随验收级别连续调节自主度。

七步闭环（一次 goal 的完整生命周期）：

① 触发cron / Web / Issue / IM / 评论 mention
→
② 执行claim 派发到机器，agent CLI 在 worktree 里干
→
③ 机器验证子任务完成判定 / 可选的 verifier run
→
④ 验收判定仲裁事务内读验收级别，决定 done / review / 重试
→
⑤ 卡点review 停车等人；approve / reject / redirect
→
⑥ 交付合并回默认分支并推送
→
⑦ 汇报评论、通知、活动时间线、RSI 分析

自主度光谱不是并列模式，而是同一个旋钮的两端——验收级别决定卡点密度：

验收级别完成时的行为适用
hitl（默认）完成即 park 到 review，人 approve 后才交付；reject 回到 active 并唤醒 owner。生产仓库、不可逆改动、需要人拍板的任务。
hootl通过终态守卫后直接 done，记录 auto_completed，跳过 review。低风险、可回滚、人已明确豁免的任务。
当前实现边界（务必区分设计与现状） DESIGN.md §5 描述的「自然语言验收策略 → 编译成机器检查 + 卡点规则」子系统的代码已退役（compiled checks/gates retired）：当前唯一的验收模式是上面的 HITL / HOOTL 二值；verification_strength、checks、setup 命令执行均不再运行。蓝图与 RSI 的 Phase A–D + §14 已落地，Phase E（评测集 / best checkpoint）已立项未实施。详见第 7 章与第 19–21 章。

2快速开始

OuroFlow 由一个 Go daemon、一个 agent/机器侧 CLI、一个 Next.js Web 控制台组成。最短可用路径是：起 daemon → 起 Web → 在 Web 里完成首次登记 → 在目标机器上 connect → 建第一个 goal。

前置版本 / 说明
Go1.26+（go.mod 声明 go 1.26.4）
Node.js / npm20+ / 10+，仅构建 Web 需要
Gitrepo 型项目与交付需要；目标机器可访问代码仓库
agent CLI目标机器上至少装一个支持 ACP 的 CLI（claude / opencode / kimi / hermes 等，见第 5 章）

构建后端与启动 daemon：

./build.sh                        # 产出 build/ouroflow 与 build/ouroflow-daemon
./build/ouroflow-daemon           # 默认监听 127.0.0.1:47813
# 可选：--db /path/to/ouroflow.db
# 监听 0.0.0.0 前必须先配置 platform.worker_token，否则启动被拒绝

启动 Web 控制台：

cd web
npm install
npm run build && npm start        # 默认 127.0.0.1:47814

开发态可用 npm run dev（同样 47814）。前端通过 Next rewrite 把 /backend、/ws、/webhooks 转发到 daemon；daemon 端口在打包时固化，改端口需要重新构建前端或重新打包。

产物 / 命令用途
build/ouroflow-daemon控制面：HTTP/WS 服务、SQLite、调度器、交付与守卫；子命令 version / paths / backup / export-template。
build/ouroflow双身份：① 注入 agent 的 PATH，作为协作工具；② ouroflow connect 把一台机器注册为执行节点。
./package.sh发布包 dist/ouroflow-v<版本>-<os>-<arch>.tar.gz：bin/ + web/ + start-all.sh，daemon 47813 / Web 47814。

在目标机器上接入执行节点：

./build/ouroflow connect --server http://127.0.0.1:47813
# 可选：--name build-box --scan ~/src --scan '~/work/*' --agents ~/.ouroflow/agents.yaml
./build/ouroflow status           # 查看 machine id、探测到的 CLI、最后一次心跳

首次登记（推荐在 Web 的「新建」页按对话引导完成，也可用 CLI）：创建项目（domain）→ 选择运行时（runtime，connect 探测后自动出现）→ 创建智能体（agent）→ 创建 goal。CLI 的 create 走的是管家登记通道：

./build/ouroflow create domain --name demo --type scratch
./build/ouroflow create agent  --name dev --runtime <runtime-id>
./build/ouroflow create goal   --title "修复登录超时" --domain demo --assignee dev

判断首次链路是否打通，看三个信号：ouroflow status 有心跳、/runtimes 出现探测到的 CLI、goal 详情出现 queued → running 的 run。若机器已注册但任务不派发，先确认 agent 绑定的 runtime 属于哪台 machine（runtime.machine_id）——daemon 不会把 run 派给「没有机器」的 runtime。

环境变量作用
OUROFLOW_HOME数据根，默认 ~/.ouroflow；生产建议独立持久目录（如 /root/ouroflow-data）。
OUROFLOW_DB单独覆盖 SQLite 路径，默认 $OUROFLOW_HOME/ouroflow.db。
OUROFLOW_SERVER_URLCLI 访问 daemon 的基地址，默认 http://127.0.0.1:47813。
OUROFLOW_DAEMON_PORT仅构建期参与前端 rewrite；运行期改它不会迁移已固化的反代目标。
OUROFLOW_COMPILE_VERSION覆盖 build.sh 的版本戳，两个二进制必须同戳。

3系统架构

OuroFlow 是控制面 / 执行面分离的单机系统：daemon 只做状态、调度与交付，真正的代码执行全部发生在运行 ouroflow connect 的机器上。daemon 从不 spawn agent 进程（早期本地 transport 已退役），这既是安全边界，也是「一台笔记本控制多台构建机」的扩展点。

进程 / 目录角色权威
ouroflow-daemonHTTP/WS 控制面；持有 SQLite；跑调度、仲裁、交付、守卫、探针与恢复循环。全部状态的唯一权威。
internal/service领域规则与事务边界：goal/run/sub-goal/change/review 的状态转换都在这里。业务规则权威（代码注释指向 DESIGN.md）。
internal/store单文件 SQLite（WAL）；schema.sql 42 张表 + 启动期增量迁移。持久化权威。
internal/daemon调度 tick、机器派发、deliver、verify/gate sweeper、watchdog、worktree 生命周期。运行时编排权威。
internal/server + internal/linkHTTP/WS 路由、鉴权；机器侧 JSON-RPC 协议常量与参数类型。接口边界。
cmd/ouroflow-cliagent 协作工具（comment / subgoal / change / env-change）+ 机器侧 connect worker + ACP 执行器。执行面。
web/、site/Next.js 控制台与独立营销站；Web 只是 daemon 的客户端，不持业务状态。展示面。

一次 goal 的数据流（以 Web 创建、机器执行为例）：

① 写入Web/CLI/cron → HTTP/JSON 或 intake → service 事务写 SQLite
→
② 提交后发事件commit 成功才 bus.Publish；事件不是真相
→
③ 调度dispatch tick 原子 Claim → 机器 PULL 队列
→
④ 执行connect 取任务 → ACP stdio → 在 worktree 改代码
→
⑤ 回传事件批量上报 → run 终态 → 仲裁事务
→
⑥ 判定与交付review / done / retry → approve 后 merge+push

模块边界：依赖方向是 server → service → store；HTTP handler 只做参数校验与调用，不自己发明状态机；daemon 只做编排、原子 stamp 与外部副作用（git / 进程 / 队列）；cmd/ouroflow-cli 只经 HTTP 或 /rpc 说话，不直接碰 daemon 的数据库。新增能力优先落在 service（规则）或 daemon（编排），跨层直写是腐化的开始。

部署形态：单机裸进程（systemd 或 start-all.sh）是最常见形态；daemon 默认只绑定 127.0.0.1，Web 同机反代。也可以把 Web 与 daemon 装在同一台机器、把 connect 指向多台构建机。没有 Kubernetes、消息队列或外部数据库依赖——SQLite 与文件系统就是全部基础设施。JEM 沙箱部署见 docs/UPGRADE.md 与第 12 章。

4核心域模型与状态机

域模型的权威定义在 docs/design/DESIGN.md §2–§6；协作对象（sub-goal / change / verification / handoff / consult）的终稿在 docs/design/Collaboration.v2.md §2、§12。这里只给出一张可工作的地图。

对象职责权威边界
domain（项目）共享仓库 + 验收级别 + 默认卡点 + git 身份/凭据 + issue/PR 映射；repo 型或 scratch 型。验收策略属于域；goal 可显式覆盖 category。
goal（任务）用户可感知的工作单元；绑定 domain、assignee（agent 或 squad）、可选蓝本版本。goal 状态是唯一权威。
run（执行实例）一次 agent 进程执行；有 run_kind（worker/processor）、role（owner/subgoal/consult/review/verify）、attempt、token。run 无权威：终态必须被仲裁事务读取后才算数。
sub_goal（子任务）goal 内的可委派工作项；不是 child goal，不可递归；assignee + verifier 分离。子任务状态机独立于 goal；Done ≠ Verified。
workspace / worktree执行隔离：run 级 workspace；repo 型项目使用每 run 一个 git worktree，分支承载检查点。workspace 属于 run，不跨 run 复用。
change / revision跨 workspace 的逻辑交付物；ready → integrating → integrated，冲突转 conflict；revision 绑定 base/head。Change 由 owner 集成，Coordinator 不执行 git。
integration（集成）owner 把 sub-goal 的 change 合入自己的 workspace；合并后的再验证是后续动作。集成动作由 owner run 执行。
verification_resultverifier 的裁决记录（passed / rejected + summary + evidence）。verifier 只产生判定，不启动下一轮。
attention派生字段：integration / wrapup / recovery / user_action，驱动 owner 的 successor run。由 Reconcile 从权威状态推导，不手写。

goal 状态机：backlog → active ↔ review → done / failed / cancelled。完成判定的关键分支都在同一条仲裁事务里：

backlog已登记未激活
→
active可 claim、可重试、可 review 往返
→
reviewhitl 完成停车；人可 approve/reject/redirect
→
done交付完成或 hootl 自动完成

旁路：failed（重试耗尽 / 不可重试错误）、cancelled（人取消，级联停 run）。reject 不新建状态，而是 review → active，human_iterations++ 并唤醒 owner。

run / sub_goal 状态：run 为 queued → running → completed / failed / cancelled；sub_goal 为 running → verifying → verified / rejected，失败分支 failed，人工放弃 cancelled。review 与 verify 是两种不同的门：review 是 goal 级人工卡点，verify 是子任务级质量判定。

四条最值钱的不变量（背下来） ① run 无权威：agent 的 stdout 永不被解析成状态，终态必须经过仲裁；② 事件不是真相：DB 是唯一真相，Reconcile 幂等、状态转移带条件；③ 每 goal 每 agent 至多一个活跃 run，owner 单飞，consult/verify/review 只读并行；④ 任何终态 run 最终必被 Reconcile——崩溃恢复靠重放，不靠内存。完整 16 条见 Collaboration.v2 §13，19 条见 DESIGN.md §9。

5调度与执行

调度器把「该谁干活」变成一条可审计的流水线：触发 → 建 goal/run → 原子 Claim → 机器 PULL → ACP 执行 → 事件回传 → Reconcile。触发渠道共享同一套幂等与去重规则。

渠道入口幂等 / 去重
定时5 字段 cron + IANA 时区；到点克隆模板建 goal。UNIQUE(schedule_id, planned_at)；错过即跳过（迟到 ≤1 分钟仍触发），不补跑。
Web / CLIPOST /goals、/intake/dispatch（对话式创建）、goal 评论 mention。评论触发按评论 ID 去重；@all 抑制自动触发。
Issue / PRGitHub / GitCode 轮询（默认 30s，下限 15s）+ webhook 双通道。source_ref 唯一；webhook 验签；每次投递（含拒绝）落 webhook_delivery。
IM 入站飞书消息 → processor run 解析意图 → 创建草稿/goal。消息 ID 去重；多项目草稿 10 分钟过期。
协作mention、sub-goal 依赖唤醒、咨询回复、review 驳回。每条触发都带 trigger_comment_id，回复自动挂到来源评论下。

队列与 Claim：dispatch tick 每 500ms 扫描；只对仍有空闲槽的 agent 发起原子 Claim（SQL 条件更新 + 每 goal 至多一个 running）；队列深度上限 64，满了退回 queued 等下一轮。worker 并发由 agent.max_concurrent（默认 1）控制；processor run 不挂 goal，不受 goal 串行限制。API 进程与执行进程之间没有 RPC 调用——机器用长轮询 PULL（daemon 最多挂 30s），60 秒未领取即判失败，保证 at-least-once 而不是「以为派了」。

run 维度取值用途
run_kindworker / processorworker 挂 goal；processor 是平台侧 LLM 执行者（intake / 路由等），goal_id=''。
run_typeintake / intake_web对话式创建与 Web 收件通道。
roleowner / subgoal / consult / review / verify决定 prompt、worktree 权限与仲裁路由。

执行协议：机器侧统一走 ACP over stdio；internal/proto 另有 JSONL / JSON-RPC 两种 backend 作为扩展位，当前派发不会选择它们。每次 run 会重写 staged AGENTS.md（人设 + RunProfile + 技能索引），把 ouroflow shim 注入 PATH，并下发 per-run token；agent 的权限请求由 autopermit 按角色策略自动应答（consult 只读，见第 11 章）。事件按 100ms 或 64 条批量回传，终态上报带 HeadSHA / SessionID / WorkDir。

失败与恢复：机器失败按 attempt ≤3 重试，退避 30s / 60s（上限 5 分钟）；确定性错误（模型/配置/认证）直接失败并标注「重试无效」。运行超 max_run_duration（默认 7200s）由 runaway reaper 标 cancelled(runaway)，不消耗 attempt；idle watchdog 2 分钟只通知、不再自动取消。daemon 启动执行一串恢复：RecoverStuckRunning（running→queued）→ 回放未仲裁终态 → 重 derive attention → verify / gate sweeper → review 窗口恢复 → 交付补偿（10 分钟一轮）。

与 DESIGN 的口径差异 DESIGN.md §5 的 verify_timeout（600s）、域 setup/verify 命令执行、worktree 干净性检查均已退役或未落地；当前「机器验证」指子任务完成后的审计记录或可选 agent verifier，不是平台执行域命令。写扩展前先核对代码，不要按旧文档实现。

6协作模型 v2

协作终稿是 docs/design/Collaboration.v2.md（Approved）。它把多 agent 协作拆成四个原语和一条变更交付链，核心原则是：Goal 定义协作目标，Run 定义执行主体，Workspace 定义执行隔离，Change 定义变更交付。当前代码已实现 Change / Revision / Integration / attention / Coordinator 主体，旧的 blocked / wait / parent goal 语义已退役；goal wait CLI 仍保留为有界等待工具（最多 10 分钟，不写 blocked 状态）。

7验收与交付

验收级别是当前唯一的验收开关，优先级：goal 显式 category → domain acceptance_level → 平台默认 hitl。接口校验只接受 hitl / hootl；domain 的清空必须走 PATCH /domains/{id}/acceptance（普通 PATCH 的空值表示保持旧值）。平台自身的 digest / team-import goal 有额外的自动批准白名单，普通任务不走该白名单。

📘 判定的三个角色

  • 定义：域所有者 / 人——选择验收级别、是否指派 verifier。
  • 执行：agent——只负责产出，不定义验收标准。
  • 判定：平台（完成守卫 + review 状态机）与人（review 卡点）；子任务可选 agent verifier。

📗 当前实际发生的判定

  • 子任务完成：无 verifier → 写一条 verification_result（machine verification passed）后转 verified；有 verifier → 派 verify run，由 verifier 用 subgoal verify --verdict 出裁决。
  • goal 完成：先过 finalization guard（未 settle 的子任务 / change / consult / ask-human / 蓝图节点），再过验收级别。
「机器验证」的现状必须说清 编译式验收（NL → checks + gates、verification_strength → 卡点密度）已退役。当前没有平台侧「跑测试 / 结构检查 / 覆盖率」的自动执行：子任务的 machine verification 是完成即记账；需要真实质量门时，显式给子任务配 verifier agent，或把测试写进 agent 的任务说明。旧文档中的 gate diff_contains、verify_timeout 均不再是运行路径。

review 卡点：hitl goal 完成即 park 到 review，review_request 记录原因；execution 被冻结（新 run 只能排队，不能 claim），intent 不被冻结。人的决策三种：approve → 写 gate_decision 并发布 goal:approved 触发交付；reject / redirect → 回 active、human_iterations++、写驳回评论并唤醒 owner。重复决定有守卫；批准后交付若失败，2 分钟宽限期内可重新批准重试。

11权限、安全与隔离

威胁模型先钉死：单用户、单机、可信本机。OuroFlow 不是多租户系统，也不假设 agent 是恶意的；它防的是「agent 手滑」「误触发」「外部 webhook 伪造」「把控制面裸奔到公网」。部署者的第一原则：不要在没有 token 与 TLS 的情况下把 daemon 暴露到非 loopback。

控制机制边界
控制面鉴权loopback 放行；非 loopback 必须 platform.worker_token（Bearer 或 ?token=，每请求现读，fail-closed）。启动时缺 token 直接拒绝监听。/rpc 与 OPTIONS 豁免；/connect 不豁免。
per-run 执行凭据Claim 时签发 run token；/rpc 用 token 解析 goal/agent/role/run，忽略 agent 自报 ID；旧 token 上报被丢弃。只对当前 run 有效。
worktree 隔离每 run 独立 workspace；repo 型项目每 run 独立 worktree；owner 分支承载检查点；consult/verify/review 不获得写权限。同一 agent 的多个 run 仍由 semaphore 控制并发。
consult 只读role=consult 在 ACP 权限层拒绝 edit/delete/move/execute/fetch；read/search/think 放行。是工具层强制，不是 OS 沙箱；恶意 CLI 仍可能绕过 ACP。
协作权限矩阵human 全可；owner 可 handoff / 建 sub-goal；assignee 只能干自己的；guest 只能评论；review/verify 只评论；squad leader 代表小队。不可递归由 schema + 参数 + 权限三重保险。
人工闸门HITL review、goal authorize（F1 授权继续）、gate 节点、危险操作二次确认。agent 无权请求审批，只能把决定权交回人。
webhook 验签每个 connection / domain 独立 secret；每次投递（含拒绝）落库；source_ref 去重。伪造请求不能创建 goal。

危险操作：取消 goal 会级联停 sub-goal 与 queued run，但保留 Change/Verification 历史；agent/squad 有活跃工作时删除被守卫拒绝，goal 删除则是物理级联（run、评论、子目标、Change/Verification 一并清理，不可恢复）；stop run 不消耗 attempt、不改 goal 状态，后续由人决定 continue 或放弃；分支清理只发生在成功/已合并/取消/删除，失败保留证据。域 git 凭据、webhook secret、平台 token 由 daemon 本地保管，安全等级取决于主机与 OUROFLOW_HOME 的文件权限——部署时应限制目录权限并备份加密。

不要把「单用户」误解成「无边界」 单用户是产品定位，不是可以省掉鉴权的理由：一旦 -addr 改成 0.0.0.0，worker_token 就是唯一的门；Web 反代也必须加认证与 TLS。agent 的执行隔离是「工作副本隔离 + 协议层权限」，不是容器/虚拟机级沙箱；需要强隔离时把 connect 跑在独立机器或沙箱里。

14结构化总纲：三层串联与双簿记

14.1 项目 – 小队 – 蓝本：三层各归其位

用户的核心设计诉求是「把项目、小队、蓝本三个概念串起来，训练后的蓝图就是真实的工作流」。落地为一张三层分工表——注意它们是软关联，goal 是唯一的汇合点，不构成硬层级：

层回答的问题结构化载体与其它层的连接
项目（domain）任务属于哪条业务线、按什么策略验收domain 表 + 验收级别（hitl / hootl）goal.domain_id；评测集（Phase E）将挂在这一层
小队（squad）有哪些岗位、谁能干什么活squad_role 注册表（角色词+岗位说明书）+ 成员名册蓝本节点写 capability:角色词 引用它；goal.assignee_type='squad'
蓝本（blueprint）按什么顺序、什么分支、什么人工卡点去执行blueprint_version（JSON 规范图，版本不可变）goal.blueprint_version_id 钉住某个已发布版本
为什么蓝本不绑项目 「修复流程」可以跨项目复用——蓝本刻意只引用能力（capability），不引用归属（domain）。绑定发生在 goal 上：一个 goal 同时声明「属于哪个项目（domain_id）」和「按哪个蓝本跑（blueprint_version_id）」。

14.2 双簿记：菜谱与做菜日志永不合并

📘 规范图（计划）

  • 来源：蓝本版本，人工或涌现固化起草
  • 属性：发布后不可变（content_hash 校验，库被旁改即拒绝编译）
  • 用途：编译源头、A/B 控制变量、审计、回滚锚点

📗 执行图（记录）

  • 来源：goal 的实体表（sub_goal/run/verification_result/…）读时装配，永远反映真实发生的事
  • 属性：永不可编辑——它就是事实
  • 用途：RSI 分析、指标度量、与规范图对照
为什么不能合并成一张图 「训练后的蓝本就是真实工作流」这句话如果理解成「把计划与记录合二为一」，会同时毁掉四样东西：A/B 复测（没有不可变的 v1 就没有控制变量）、回滚（goal 钉旧版本即回滚）、审计（谁改过图说不清）、守卫（全节点终态判据要求图先于执行存在）。正确姿势：蓝本版本=菜谱，执行图=做菜日志，训练是两者之间的桥7。

15.2 六类节点全景

类型语义编译产物与运行方式专属字段
task 任务 一个可执行的工作项，必有执行者与验收 编译成一个 sub_goal；依赖全 verified 后释放运行；完成走机器验收 / verifier agent 复核 assignee（agent: / squad: / capability:）、brief（支持模板）、verify{mode, verifier}
condition 条件 启动时一次性求值的确定性分流16 编译期求值（只允许引用 goal 字段），未选中的分支连同后代标记 skipped，不产生 sub_goal expr（如 goal.category == "hitl"）、cases[{id,test}]、else
router 路由 受限弹性：LLM 从注册类里选一个1 编译成一个「分类 run」（决策执行者=leader）；输出契约是围栏 JSON {"class":"quick"}；未命中/乱写/无围栏 → 一律 fallback，永不重试；决策快照进 resolved_config 可审计 classes[{id,title,description}]≥2、fallback（必填）、budget

15.4 版本模型与编译

  • 版本三态：draft（可编辑）→ published（不可变，goal 只能钉 published）→ 改进永远走 NewDraft 开 vN+1 继承内容。发布版本=天然的 A/B 控制变量与回滚锚点1314。
  • 两拍编译（goal 激活时，单事务）：拍 1 建结构——condition 求值剪枝、全部可执行节点编译成 sub_goal（带 depends_on 门控，挂起的子任务不产生 run）、capability 解析成具体 agent、spawn/router 准备好各自的输出契约；拍 2 填参数——每个子任务被依赖释放时，把 brief 里的 {{node.X.output}} 解析成上游的 result_summary 快照。计划先于执行存在，这正是守卫能数「还差谁没跑」的前提。
  • Squad 节点的编译：写 squad:xx 的节点编译到该队队长——认领机制要求真实 agent，把活派给一个"队"只会造成永无人认领的死锁（Phase B 修掉的真实 bug）28。

16Agent 小队的结构化：从「自然语言派工」到「角色词汇表」

16.1 旧病灶 → 新结构

❌ 旧：自由文本角色

squad_member.role 是任意字符串，playbook 用自然语言写「让擅长修复的人去修」——解析靠 LLM 猜，同一个人这轮叫"开发"下轮叫"工程师"。

✅ 新：角色词汇表（squad_role）

小队注册封闭词汇表：每个角色词 = ^[a-z][a-z0-9_-]*$ 的 slug + 岗位说明书（description，喂给 spawn 规划者做派工依据）。蓝本节点写 capability:implementer 引用岗位而不是具体人。

🔒 词表门（fail-closed）

注册过词汇表的小队，添加成员时角色必须来自词表（或保留词 reviewer / member），否则拒绝；角色有人携带时该词不可删除。没注册的小队保持自由文本兼容——存量团队零破坏。

16.2 capability 的确定性解析规则

编译期（不是运行时、不是 LLM）把 capability:implementer 解析成具体 agent，规则全透明：

步骤规则
1 匹配域goal 绑定的小队（多小队简报的空白在 Phase B 补齐为节点级 team_squad_id）
2 词汇匹配LOWER(TRIM(role)) 规范形 == 请求的 slug——大小写、首尾空格全部归一
3 结构排除reviewer 岗位结构性排除（Player-Referee：裁判不能下场踢球）
4 负载均衡多人命中 → 选非终态子任务最少的（按 assignee 或 verifier 身份计数）；平局取 created_at 最早——同输入必同输出，可复现可 A/B
5 快照解析结果写进 blueprint_node.resolved_config（assignee_spec / resolved_agent / team_squad_id）——谁被选中、为什么，永久可审计
6 零命中fail-closed：激活失败、goal 留在 backlog，错误信息直接列出该队现有词汇（"roles present in this squad: [design-implementer, proprietary-implementer]"），照着补人或改词即可
技能轴的取舍（§11.8）：为什么「专有技能」编码进角色词，而不是做成第二根轴 曾有设想：A、B 角色相同但各挂不同 skill，调度按 capability:implementer + skill:某技能 双轴交集选人。被否决，理由有二：① 双轴会产生"半命中态"（能力命中技能不命中），错误信息说不清缺哪根轴；② skill 是动态配置、role 是静态声明，两轴天然漂移，会腐蚀 resolved_config 的 A/B 控制变量。定稿：技能差异=岗位差异——design-implementer 与 proprietary-implementer 是两个岗位，词汇表单轴封闭的立论得以保持。选错人不会干错事：走 verify 失败 → 有界重试 → 失败的安全路径，浪费的只是几轮重试。

16.3 spawn：队内扇出的结构化通道

旧模式里「队长拿到任务再临时拆给队员」是漏跑/乱序的重灾区。spawn 节点把这个弹性装进契约：

  1. 编译期 spawn 变成一个「规划者 sub_goal」，brief 附带输出契约：围栏 JSON 清单 [{title, brief, assignee}]，明确「按角色词派工、分给擅长的人而不是空闲的人、名册里的技能注在括号里」；
  2. 规划者完成后，平台（确定性代码，不是 LLM）物化每项为真 sub_goal，全部挂到 spawn 上，下游节点自动追加依赖全部子项——复用同一套 wake 门控；
  3. 违规即拒：派给名册外成员、超出 max_children（上限 8）、输出不成契约 → 违规计数 +1 并重试（≤3 次），耗尽则失败并级联——契约保证拆解产物一定合法；空清单合法（这活确实不用拆）。

19自迭代的完整流程：优化闭环怎么做

19.1 主循环：七步一闭环

① 执行goal 钉蓝本版本跑，产出执行图（只读事实）
→
② 度量执行图实时装配指标（结构/时间/质量）
→
③ 发现RSI 九类结构分析，产出 finding
→
④ 提案结构化补丁（5 种操作符），翻译者=人 或 Phase D 确定性翻译器
→
⑤ 批准人工批准 → 开新草稿，changelog=假设
→
⑥ 复测同题 A/B：两个 goal 钉 v1/v2 各跑一次，七项指标对比
→
⑦ 采纳指标支持假设 → 发布 v2；不支持 → 拒绝，v1 不受任何影响
⑦ 之后回到 ①，下一轮迭代开始 —— 每一轮的产物都是不可变版本链上的一环，可回滚可审计

19.2 每一步的关键机制

  • 提案是结构化补丁，不是自然语言建议。五种操作符：add_node / update_node / delete_node / add_edge / delete_edge2122。创建提案时立即把补丁应用到基准版本上跑全部 V1–V6 校验——不合法的提案根本进不了列表；批准时再校验一次（防库被旁路改动后漂移）。批准的语义=以假设（hypothesis）为 changelog 开新草稿，不自动发布；重复批准/拒绝已被决策的提案 → 结构化冲突拒绝。
  • diff 是三色的、可读的：改动前后两张规范图并排渲染 + 节点增删改/边增删清单（+绿 −红 ±黄），人不用读 JSON26。
  • Phase D 确定性翻译器（机器翻译 finding 的第一条通道）：目前只翻 serial_chain（关键路径 ≥4 节点）为「并行化串行链」提案，且带四道安全检查——goal 必须钉版本（infer 不翻）、链上 brief 双向查 {{node.X.output}} 数据引用（有真依赖就不许并）、以spec 图为真相核对链形、补丁 all-or-nothing。触发不了就静默跳过，产出仍是 pending 提案，永不自动发布。其余八类 finding 一律人工翻译——LLM+P 分工：模型只建议，合法性交给确定性校验器23。
  • 同题 A/B：没有评测集之前，复测=人挑两个可比的 goal 分别钉 v1/v2 跑同类任务，A/B 卡并排七项指标 + Δ。采纳标准不是"全面变好"而是效率指标改善且质量指标不掉。

19.3 入口坡道：涌现固化（infer → blueprint 的收敛通道）

infer 执行goal 不绑蓝本，owner 动态拆解（弹性全保留）
→
签名记录每次 done 都记形状签名进 infer_shape（L1 精确 + L0 骨架）
→
3 次同构同域连续 3 次签名全等 → 判定"这已经是事实上的固定流程"
→
自动起草 v1确定性翻译执行图→蓝本草稿（只起草，永不自动发布）

这是「第三派动态多 agent」向「图即代码」收敛的通道1127：弹性先自由地试，试出稳定形状后沉淀为可版本化、可 diff、可优化的规范。起草名撞名即跳过（签名即命名键，天然去重不堆积）。

人工闸门清单——闭环里永远属于人的四个按钮 批准提案（机器只许起草）· 发布版本（草稿永远不生效）· 采纳结论（A/B 只呈现证据，不替人拍板）· gate 拍板（超时有兜底分支，但默认等人）。自动化的上限被明确设计在这里：平台永远不机器自批机器提案2025。

21收敛条件怎么定义

21.1 涌现固化的收敛：双层签名（§14.1）

收敛判定不引入任何 LLM 判断，两层都是确定性多重集哈希，可解释可复现：

镜头看什么收敛条件触发动作
L1 精确全部节点 kind 多重集 + (from|to|edge) 三元组多重集同域最近 3 条 全量同构起草「固化：签名·域名」
L0 骨架剥掉运行间噪声：verify/review/consult 节点、seq/verified_by/consult 边3 条骨架同构（L1 允许不同——多一轮咨询、一次返工不再破坏收敛）起草「近似固化：骨架签名·域名」
  • 近似固化按 L0 骨架签名为命名键——后续 near-miss 继续去重进同一份草稿，不堆积；
  • 两层都只起草、不发布：误命中最坏结果=多一份等人审的零风险草稿（宁欠勿滥）；欠触发代价也为零（infer 弹性全在，不收敛就不固化，没有任何损失）；
  • 诚实标注：多重集签名是便宜的滤网，不是图 canonization——它做的是"够用的收敛检测"，不是"形状等价判定"。

21.2 迭代轮次上限：rsi.max_auto_rounds（§14.2）

  • 配置在 app_settings 表，默认 10；0=关闭自动产出；改完即生效，无需重启。
  • 只封机器的自动工件：涌现固化按域计（infer_shape.drafted 行数）、翻译器按 distinct blueprint 计（pending/approved 的 rsi-translator 提案）。
  • 分析永不被封（可见性不倒退：finding、报告、metrics 照常产出）；人工动作永不在内（人批多少提案、发多少版本都不限）——上限防的是"机器自己刷自己"，到上限只记日志跳过，不报错不断流。

21.3 采纳的收敛与未来条件（Phase E 立项）

  • 现在：采纳=同题 A/B 七项指标支持假设（效率改善且质量不掉）+ 人拍板发布。
  • Phase E 评测集（§14.3）：domain 声明 eval_goals 题库，mode=eval 对每道题两版本各真实跑一次，聚合从单对 delta 升级为集合均值 + 符号显著性检验（min_pairs=5 才有结论）27，达标才允许采纳建议。成本诚实说明：复测=真实执行=花钱花时间，这正是它没有被塞进本轮的原因。
  • Phase E best checkpoint（§14.4）：版本链已经是全量 checkpoint，缺的只是"哪个最好"的标注——补 blueprint.best_version_id 人工列、A/B 卡「设为最佳」、列表徽章、绑定默认选中。语义边界：标注不是开关，不自动切流量。AFlow 调研的教训：checkpoint 的价值在检索与复用，不在存储1819。

23终章：一个完整迭代的实践案例

以下用一个虚构但机制严格对齐的 Go 服务维护团队（域 go-service，小队 go-dev-squad：队长 go-owner、两名 implementer、一名 reviewer），把前面所有章节串成一条时间线。数字为演示数据，每一幕都标注了它演示的机制。

第 0 幕 · 自由生长：三次 infer 执行演示机制：infer 弹性 · 形状签名记录 · 运行间噪声（→ 第 6.3 / 8.1 节）

团队尚未绑任何蓝本。三个线上 bug（#114、#117、#121）先后交给 owner，它每次都临场拆成三步：复现 → 修复 → 验证，拆解略有差异但骨架一致。第三次（#121）修复前 owner 还向队长发起了一轮 consult——多出来的咨询就是「运行间噪声」。

每次 goal 跑到 done，平台记一条形状签名进 infer_shape：L1 全量签名三次不全等（#121 多了 consult 节点），但 L0 骨架签名——剥掉咨询/验证/评审噪声后——三次全等。

第 1 幕 · 涌现收敛：自动起草「近似固化」演示机制：L0/L1 双层签名 · 只起草不发布 · 人工审查补强（→ 第 2、8.1 节）

#121 终态落账的瞬间，收敛条件命中：同域最近 3 条 L0 骨架同构。蓝本列表里自动出现一份草稿：

名称：近似固化：a3f9c210·go-service
描述：自动起草（近似固化）：同域连续 3 个 infer 执行图骨架同构（细节有差异），
      由平台确定性翻译生成（§14.1 L0 骨架收敛）。请审查后发布；发布前不影响任何任务。
结构：t_repro(复现) → t_fix(修复) → t_verify(验证) → end_ok

机器不做的事，人做：go-owner 审查这份草稿，补上它看得到而签名看不到的东西——给 t_verify 配 verifier=reviewer（Player-Referee：修复者不能自己验自己），并把「跑哪些测试、查哪些竞态」写进 t_fix 与 t_verify 的 brief——当前平台不代跑域 Checks，machine 档只记录完成结论，真实质量门要靠 verifier 执行并给证据。t_fix 的 brief 还要写上 {{node.t_repro.output}}（修复必须引用复现结论）。逐项校验通过 → 发布 v1。

从这一刻起，go-service 的新任务有了一种新选择：不绑蓝本=继续自由拆解（第 0 幕模式）；绑 v1=享受确定性保证。

第 2 幕 · 图说了算：一次被守卫护航的执行演示机制：两拍编译 · guard · 结构拒绝 · 死分支剪除（→ 第 15.4、17 章）

bug #131 进来，goal 绑 v1 激活。编译拍 1：3 个 sub_goal 一次全部建出（t_repro 立即开跑，t_fix/t_verify 按 depends_on 挂起）；拍 2：t_repro verified、t_fix 被释放的瞬间，brief 里的 {{node.t_repro.output}} 解析成复现结论的快照。

中途 owner 试图 subgoal create 加一个「顺手写个补丁说明」的子项——被结构拒绝挡回："goal is blueprint-driven: sub-goals are compiled from the blueprint, not created ad hoc"。它改用在目标下评论转达想法（契约允许的汇报通道）。

t_verify 的机器验收第一轮没过（竞态检查 fail），重试第 2 轮通过。goal 完成时守卫核对：规范图 4 个节点全 settle（3 个 settled + end_ok）→ 放行 done。任务页并排两张图：teal 的规范图（计划）与蓝色执行图（记录），形状完全一致——这就是双簿记给人看的形态。

第 3 幕 · 发现与提案：机器的安全边界 + 人的翻译演示机制：RSI serial_chain · 翻译器数据流守卫 · 人工结构化补丁 · 三色 diff（→ 第 19.2 节）

训练分析对 #131 的执行图跑 RSI：关键路径 6 个节点（3 task + 3 verify）≥ 阈值 4 → 产出 serial_chain finding：「复现→修复→验证被人为串行化」。

Phase D 翻译器先试：把链上的 task 映射回 spec 节点 → 数据流检查发现 t_fix 的 brief 含 {{node.t_repro.output}}——存在真实数据依赖，翻译器正确地放弃自动提案（数据流守卫生效，宁可不提也不提错）。机器知道自己的边界。

人来翻译：go-owner 读 finding，做出机器做不到的语义判断——「复现」里其实含两件事：搭修复分支环境（与复现无数据依赖，可提前并行）和「跑出最小复现」（修复的硬依赖）。手工起草结构化补丁提案：

hypothesis：把环境搭建从复现中拆出并行，缩短关键路径（expected: critical_path_ms ↓）
patches：
  - op: add_node   node: { id: t_env, type: task, title: 搭建修复分支环境, … }
  - op: add_edge   edge: { source: t_env, source_handle: "done", target: t_fix }
  - op: update_node node: t_repro（brief 收窄为纯复现）

第 5 幕 · 环境继续收敛（展望）演示机制：迭代上限 · Phase E 的两个候选能力（→ 第 8.2/8.3 节）

闭环继续滚动：若后续又出现 3 次新形状的同构执行，会再起草一份近似固化草稿——但该域 drafted 计数已 +1，自动产出向 rsi.max_auto_rounds（默认 10）逼近；到达上限后机器只记日志不再自动起草，而人随时可以继续：人工提案、批准、发布不受任何限制。RSI 分析与指标照常产出——被封的只有"机器自动开新工件的笔"，不是"机器的眼睛"。

Phase E 落地后的后续剧本：go-service 域声明评测集 {#131, #135, #138, #142, #146…}，mode=eval 让 v3 候选对整个题库自动复测，集合均值 + 符号检验（5 对起判）替代手工挑题；跑赢后在 v3 上点「设为最佳」，列表页挂出「最佳 v3」徽章，新任务绑定时默认选中——版本链这台"仓库"终于有了检索索引。

这条时间线就是平台的自我描述：infer 自由地长（第 0 幕）→ 骨架收敛成规范（第 1 幕）→ 规范被结构强制地执行（第 2 幕）→ 执行反过来优化规范（第 3–4 幕）→ 优化被护栏与人的拍板权约束着滚向下一轮（第 5 幕）。图说了算，而图本身，也是可以被锻造的。

24.8 拿到指标怎么分析（五步法）

  1. 先看三个数：work_sum、wall、critical_path → 手算 gain = work/cp（上限）、speedup = work/wall（实际）、loss = wall−cp（浪费）。
  2. 四象限定位（下表），先判断「有没有并行空间」再判断「为什么没用上」。
  3. 拆 loss：dependency_wait 大 → 先减依赖；dispatch_wait 大 → 加并发/改派发；human_wait_share ≥0.30 → 查 gate。
  4. 看形状：width_peak=1 → 从未并行；width_peak 高但 speedup 低 → 有段是瓶颈，回 cp 找那段；lane_imbalance 高且 width_peak 高 → 并发开了但活给同一个人排队。
  5. 用账本验证：单次运行只提假设；判定必须看 rsi_round 同 domain 相邻两轮的冻结 delta（方向是否符合提案的 expected_direction）。
gain（上限）speedup（实际）loss 主成分结论与动作
≈1≈1小依赖链本身就是唯一路径：无并行空间。若链深 ≥4 → serial_chain，先审「依赖是否人为」
≥2< 0.7×gain依赖等待大能并行却没并行 → serial_chain / lost_parallelism → chain→fork 提案
≥2< 0.7×gain派发等待大、lane 失衡派了但全压一人 → wrong_assignee → 改 capability 或加并发
≥2≈gain小健康，无需动作

分档参考：loss/wall <5% 几乎无等待（要提速只能减 cp）；5%–30% 有真实空档（查拆项）；>30% 调度/依赖问题压过执行问题（先修结构再加人）。speedup 分档：<1 墙钟里全是空档；1–1.5 全串行；1.5–2.5 双车道；>3 良好并行。

这里的关键判断：gain=1.0，所以 lost_parallelism（要求 gain≥2.0）不会命中。系统判断「该并行」靠的不是统计学，而是结构学：serial_chain 命中（depth≥4），且翻译器证明「四个 brief 之间零数据引用」——这是确定性证据，说明这条链的依赖是人为的、拆掉不破坏语义。所以 Phase D 只翻译 serial_chain，不翻译 lost_parallelism。

v2（fork 后，仍是 4 个不同 agent）：

work_sum = 180s   wall = 47s   critical_path = 46s
gain      = 3.91  speedup = 3.83  serialization_loss = 1s
width_peak = 4    lane_count = 4  lane_imbalance = 1.00
rsi_round: round_no=2  delta: wall_ms −74.2%  parallel_speedup +286.9%

反例（fork 了但四个任务派给同一个 agent）：

work_sum = 180s   wall = 184s   speedup = 0.98  width_peak = 1
lane_count = 1 → lane_imbalance = 1.00（永远不触发）

此时派发堆积不会显示为 lane 失衡，而是表现为 width_peak 不上去、speedup 不涨——这就是 11.5 末尾「三指标一起看」的原因。

24.10 口径与坑（速查）

  • review 不参与 work_sum、critical_path、lane、wall 的端点——否则一次长评审会污染全部指标；它只进 review_busy_ms / review_overhead_ratio。
  • 机器校验留 0 时长节点：会进 depth 与路径，但不进 work_sum/lane；这解释了「depth 比 task 数大」。
  • cp 只认显式边：seq（时间先后推断）只做展示/排队分析，永不进关键路径；否则每次串行执行都会被误判成 1.0× 串行链。
  • speedup ≠ gain：前者是实际、后者是上限；判断「依赖过强」看 gain 与 speedup 的差，判断「派发不足」看 dispatch_wait 与 lane。
  • loss 不可硬拆：三项等待之和不一定等于 wall−cp（口径不同）；它们用于定位方向。
  • 数据只在 train 模式采集：infer 零采集、没有执行图可分析；且 goal 必须已终态（done/failed）才会冻结并分析。
  • 单节点内部并行看不见：一个 agent 顺序干四件事，图上仍是一个节点——这类只能靠 split_candidate（若该节点占 cp ≥45% 且不止一个）或人自己拆 brief/skill。
  • baseline 与 delta 不是一回事：baseline = 同 domain 最近 20 个 ready 会话中位数（样本<5 为空）；delta = 与同 domain 上一条 rsi_round 比。A/B 结论只认 delta。

  1. 1OpenAI · Structured Outputs（2024-08） —— 受约束解码把「只能输出合法 JSON」变成解码器事实：官方对比是 prompting 遵从率 <40%、受约束解码 100% 合法；发布文同时承认模型行为 inherently non-deterministic。 用在哪：s0「提示词是概率指令」；2.2 router（LLM 只能从注册类里选，枚举 schema 收口）。 openai.com/index/introducing-structured-outputs-in-the-api
