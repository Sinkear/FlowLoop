0导读：三分钟看懂这一代改了什么

一句话药方 旧模式的病根是「自然语言是编排权威」——团队 playbook 用 prose 写执行顺序，靠大模型自觉遵从。 新一代只做一件事：把「谁、按什么顺序、依赖什么、验收什么」从提示词里搬进结构化数据，让代码去强制。 口号是 “prompt states, code enforces”（提示词陈述，代码强制）。

旧模式的三个痛点，以及各自的归因：

执行顺序不固定、漏跑环节 squad.instructions 是自然语言 playbook，注入简报靠 LLM 自觉3；sub_goal.depends_on 引擎本身是确定性 DAG 门控，但「要不要声明依赖」由 leader 临场决定；观察图只记录已发生的事，没有规范图就没有「全节点终态」的完成判据 蓝本 JSON 定义规范图，激活时编译成带依赖的子任务；finalization guard 计数未 settle 的节点——漏跑成为结构性阻断

1结构化总纲：三层串联与双簿记

1.1 项目 – 小队 – 蓝本：三层各归其位

用户的核心设计诉求是「把项目、小队、蓝本三个概念串起来，训练后的蓝图就是真实的工作流」。落地为一张三层分工表——注意它们是软关联，goal 是唯一的汇合点，不构成硬层级：

层回答的问题结构化载体与其它层的连接
项目（domain）任务属于哪条业务线、按什么策略验收domain 表 + 冻结的验收策略 Checksgoal.domain_id；评测集（Phase E）将挂在这一层
小队（squad）有哪些岗位、谁能干什么活squad_role 注册表（角色词+岗位说明书）+ 成员名册蓝本节点写 capability:角色词 引用它；goal.assignee_type='squad'
蓝本（blueprint）按什么顺序、什么分支、什么人工卡点去执行blueprint_version（JSON 规范图，版本不可变）goal.blueprint_version_id 钉住某个已发布版本
为什么蓝本不绑项目 「修复流程」可以跨项目复用——蓝本刻意只引用能力（capability），不引用归属（domain）。绑定发生在 goal 上：一个 goal 同时声明「属于哪个项目（domain_id）」和「按哪个蓝本跑（blueprint_version_id）」。

1.2 双簿记：菜谱与做菜日志永不合并

📘 规范图（计划）

  • 来源：蓝本版本，人工或涌现固化起草
  • 属性：发布后不可变（content_hash 校验，库被旁改即拒绝编译）
  • 用途：编译源头、A/B 控制变量、审计、回滚锚点

📗 执行图（记录）

  • 来源：goal 的实体表（sub_goal/run/verification_result/…）读时装配，永远反映真实发生的事
  • 属性：永不可编辑——它就是事实
  • 用途：RSI 分析、指标度量、与规范图对照
为什么不能合并成一张图 「训练后的蓝本就是真实工作流」这句话如果理解成「把计划与记录合二为一」，会同时毁掉四样东西：A/B 复测（没有不可变的 v1 就没有控制变量）、回滚（goal 钉旧版本即回滚）、审计（谁改过图说不清）、守卫（全节点终态判据要求图先于执行存在）。正确姿势：蓝本版本=菜谱，执行图=做菜日志，训练是两者之间的桥7。

2图的结构化：蓝本（Blueprint）

2.1 一个蓝本长什么样

蓝本内容是一份 JSON 规范图。下面这个节选（删减自内置模板「人工门审批」）展示了全部核心要素——节点、类型专属字段、边与分支端口：

{
  "name": "发布前人工审批流",
  "nodes": [
    { "id": "n_proposal", "type": "task",   "title": "产出发布方案",
      "task": { "assignee": "agent:1d5ff0af…", "brief": "起草方案，说明变更点与影响面",
                "verify": { "mode": "machine" } } },
    { "id": "n_gate",      "type": "gate",   "title": "人工拍板",
      "gate": { "prompt": "方案由 {{node.n_proposal.output}} 生成，请放行或驳回",
                "actions": [ { "id": "approve", "label": "放行" },
                            { "id": "reject",  "label": "驳回" } ],
                "timeout": { "after": "24h", "action": "reject" } } },
    { "id": "t_ship",      "type": "task",   "title": "执行上线", "task": { … } },
    { "id": "t_rework",    "type": "task",   "title": "返工修改", "task": { … } },
    { "id": "end_ok",      "type": "end",    "title": "成功收口", "end": { "outcome": "success" } }
  ],
  "edges": [
    { "source": "n_proposal", "source_handle": "done",    "target": "n_gate" },
    { "source": "n_gate",      "source_handle": "approve", "target": "t_ship"   },
    { "source": "n_gate",      "source_handle": "reject",  "target": "t_rework" },
    { "source": "n_gate",      "source_handle": "timeout", "target": "t_rework" },
    { "source": "t_ship",      "source_handle": "done",    "target": "end_ok"   }
  ]
}

读图规则一句话：分支不藏在 if-else 文字里，编码在边的 source_handle 端口上1217。gate 走了 approve 端口，就只有 t_ship 这条分支会被释放，其余分支连同后代一起剪除。

2.2 六类节点全景

类型语义编译产物与运行方式专属字段
task 任务 一个可执行的工作项，必有执行者与验收 编译成一个 sub_goal；依赖全 verified 后释放运行；完成走机器验收 / verifier agent 复核 assignee（agent: / squad: / capability:）、brief（支持模板）、verify{mode, verifier}
condition 条件 启动时一次性求值的确定性分流16 编译期求值（只允许引用 goal 字段），未选中的分支连同后代标记 skipped，不产生 sub_goal expr（如 goal.category == "hitl"）、cases[{id,test}]、else
router 路由 受限弹性：LLM 从注册类里选一个1 编译成一个「分类 run」（决策执行者=leader）；输出契约是围栏 JSON {"class":"quick"}；未命中/乱写/无围栏 → 一律 fallback，永不重试；决策快照进 resolved_config 可审计 classes[{id,title,description}]≥2、fallback（必填）、budget
gate 人工门 把「等人拍板」写进图里 编译成持有者 sub_goal 但永不入队执行15；依赖就绪后持门（held_since 计时），决策卡出现在任务页；人拍板或超时 sweeper 按声明动作自动走；非选中分支剪除 prompt、actions[{id,label}]、timeout{after, action}
spawn 派生 队内扇出的结构化通道（动态拆解的弹性口袋） 编译成一个「规划者 run」，输出围栏 JSON 子任务清单 [{title,brief,assignee}]；平台物化成真 sub_goal 并把下游挂到全部子项上；成员越界/超上限→违规重试（≤3）后失败 assignee、brief、child_type:"task"、max_children（0–8）
end 终点 收口，标记成败 ledger 行：全部活路径任务 settle 后翻 settled；outcome 记入 resolved_config outcome: success|failure
「固定节点 + 弹性环节」怎么同时成立 弹性被装进三个受控口袋，而不是散落在提示词里：router（选择自由、选项封闭）、spawn（拆解自由、契约封闭、产物必过校验）、节点内 brief（表达自由、结构封闭）。第四个口袋是整个 infer 模式：goal 不绑蓝本时，一切照旧由 owner 动态拆解——两种模式共存，互不强制4911。

2.3 发布前的六道校验（V1–V6）

校验校验什么（发布门全部 fail-closed：不过不许发布）
V1 形状节点 id 匹配 ^[a-z][a-z0-9_]{0,63}$；边引用的节点存在；source_handle 必须是源节点声明过的端口（task 隐式端口 done/failed；condition=cases[].id+else；router=classes[].id+fallback；gate=actions[].id+timeout）；重复出边拒绝；各类型 body 完整性（router ≥2 类、gate 超时可解析等）
V2 可达无环（Kahn）；根必须是 task|spawn（决策节点必须有上游语境）；从根前向可达全部节点；从 end 后向可达全部节点——没有孤岛，没有死路
V3 端口每个声明的分支端口必须有出边：condition 每 case、router 每 class + fallback、gate 每 action + timeout；gate 的 timeout 端口必须与 timeout.action 同向（无人值守路径的结构声明与行为编码不得漂移）
V4 指名agent:xx / squad:xx 必须解析到已注册实体（capability: 只查词形，真实解析在编译期 fail-closed——因为词汇域取决于 goal 绑的小队）
V5 模板{{goal.*}} 引用限白名单 9 字段；{{node.<id>.output}} 的目标必须是 task 节点且是上游——解析不了的引用在发布时就被拒绝，而不是运行时留空洞
V6 完整性content_hash = sha256(content) 落库；每次读取重新校验，库被旁路改动（漂移）即拒绝编译——激活时若校验失败，goal 留在 backlog，绝不带着一张说不清来路的图开跑

2.4 版本模型与编译

  • 版本三态：draft（可编辑）→ published（不可变，goal 只能钉 published）→ 改进永远走 NewDraft 开 vN+1 继承内容。发布版本=天然的 A/B 控制变量与回滚锚点1314。
  • 两拍编译（goal 激活时，单事务）：拍 1 建结构——condition 求值剪枝、全部可执行节点编译成 sub_goal（带 depends_on 门控，挂起的子任务不产生 run）、capability 解析成具体 agent、spawn/router 准备好各自的输出契约；拍 2 填参数——每个子任务被依赖释放时，把 brief 里的 {{node.X.output}} 解析成上游的 result_summary 快照。计划先于执行存在，这正是守卫能数「还差谁没跑」的前提。
  • Squad 节点的编译：写 squad:xx 的节点编译到该队队长——认领机制要求真实 agent，把活派给一个"队"只会造成永无人认领的死锁（Phase B 修掉的真实 bug）28。

3Agent 小队的结构化：从「自然语言派工」到「角色词汇表」

3.1 旧病灶 → 新结构

❌ 旧：自由文本角色

squad_member.role 是任意字符串，playbook 用自然语言写「让擅长修复的人去修」——解析靠 LLM 猜，同一个人这轮叫"开发"下轮叫"工程师"。

✅ 新：角色词汇表（squad_role）

小队注册封闭词汇表：每个角色词 = ^[a-z][a-z0-9_-]*$ 的 slug + 岗位说明书（description，喂给 spawn 规划者做派工依据）。蓝本节点写 capability:implementer 引用岗位而不是具体人。

🔒 词表门（fail-closed）

注册过词汇表的小队，添加成员时角色必须来自词表（或保留词 reviewer / member），否则拒绝；角色有人携带时该词不可删除。没注册的小队保持自由文本兼容——存量团队零破坏。

3.2 capability 的确定性解析规则

编译期（不是运行时、不是 LLM）把 capability:implementer 解析成具体 agent，规则全透明：

步骤规则
1 匹配域goal 绑定的小队（多小队简报的空白在 Phase B 补齐为节点级 team_squad_id）
2 词汇匹配LOWER(TRIM(role)) 规范形 == 请求的 slug——大小写、首尾空格全部归一
3 结构排除reviewer 岗位结构性排除（Player-Referee：裁判不能下场踢球）
4 负载均衡多人命中 → 选非终态子任务最少的（按 assignee 或 verifier 身份计数）；平局取 created_at 最早——同输入必同输出，可复现可 A/B
5 快照解析结果写进 blueprint_node.resolved_config（assignee_spec / resolved_agent / team_squad_id）——谁被选中、为什么，永久可审计
6 零命中fail-closed：激活失败、goal 留在 backlog，错误信息直接列出该队现有词汇（"roles present in this squad: [design-implementer, proprietary-implementer]"），照着补人或改词即可
技能轴的取舍（§11.8）：为什么「专有技能」编码进角色词，而不是做成第二根轴 曾有设想：A、B 角色相同但各挂不同 skill，调度按 capability:implementer + skill:某技能 双轴交集选人。被否决，理由有二：① 双轴会产生"半命中态"（能力命中技能不命中），错误信息说不清缺哪根轴；② skill 是动态配置、role 是静态声明，两轴天然漂移，会腐蚀 resolved_config 的 A/B 控制变量。定稿：技能差异=岗位差异——design-implementer 与 proprietary-implementer 是两个岗位，词汇表单轴封闭的立论得以保持。选错人不会干错事：走 verify 失败 → 有界重试 → 失败的安全路径，浪费的只是几轮重试。

3.3 spawn：队内扇出的结构化通道

旧模式里「队长拿到任务再临时拆给队员」是漏跑/乱序的重灾区。spawn 节点把这个弹性装进契约：

  1. 编译期 spawn 变成一个「规划者 sub_goal」，brief 附带输出契约：围栏 JSON 清单 [{title, brief, assignee}]，明确「按角色词派工、分给擅长的人而不是空闲的人、名册里的技能注在括号里」；
  2. 规划者完成后，平台（确定性代码，不是 LLM）物化每项为真 sub_goal，全部挂到 spawn 上，下游节点自动追加依赖全部子项——复用同一套 wake 门控；
  3. 违规即拒：派给名册外成员、超出 max_children（上限 8）、输出不成契约 → 违规计数 +1 并重试（≤3 次），耗尽则失败并级联——契约保证拆解产物一定合法；空清单合法（这活确实不用拆）。

4篡位残留怎么治：四道结构性闸门

「管家篡位」的本质：owner 拥有真实可写的 worktree 和自由工具面，唯一的防线是提示词里那句「请委派」5。Phase A/B 给它上了四道结构闸门——不是更严厉的措辞，而是绕不过去的代码：

闸门机制效果

5管家角色的更新：从「大管家」到三个各司其职的身份

历史锚点——旧管家提示词（agent.go:23）只有一句话的职责面：

StewardSystemPrompt = "你是一位严谨周到的管家。职责：接收主人指令、拆解并委派给合适的执行者、

它同时承担三个角色：规划（拆解）+ 执行（跟进，且能亲自干）+ 调度（派发）。三权于一身、全靠自觉，正是篡位的温床。新一代把三权拆开：

6自迭代的完整流程：优化闭环怎么做

6.1 主循环：七步一闭环

① 执行goal 钉蓝本版本跑，产出执行图（只读事实）
→
② 度量执行图实时装配指标（结构/时间/质量）
→
③ 发现RSI 九类结构分析，产出 finding
→
④ 提案结构化补丁（5 种操作符），翻译者=人 或 Phase D 确定性翻译器
→
⑤ 批准人工批准 → 开新草稿，changelog=假设
→
⑥ 复测同题 A/B：两个 goal 钉 v1/v2 各跑一次，七项指标对比
→
⑦ 采纳指标支持假设 → 发布 v2；不支持 → 拒绝，v1 不受任何影响
⑦ 之后回到 ①，下一轮迭代开始 —— 每一轮的产物都是不可变版本链上的一环，可回滚可审计

6.2 每一步的关键机制

  • 提案是结构化补丁，不是自然语言建议。五种操作符：add_node / update_node / delete_node / add_edge / delete_edge2122。创建提案时立即把补丁应用到基准版本上跑全部 V1–V6 校验——不合法的提案根本进不了列表；批准时再校验一次（防库被旁路改动后漂移）。批准的语义=以假设（hypothesis）为 changelog 开新草稿，不自动发布；重复批准/拒绝已被决策的提案 → 结构化冲突拒绝。
  • diff 是三色的、可读的：改动前后两张规范图并排渲染 + 节点增删改/边增删清单（+绿 −红 ±黄），人不用读 JSON26。
  • Phase D 确定性翻译器（机器翻译 finding 的第一条通道）：目前只翻 serial_chain（关键路径 ≥4 节点）为「并行化串行链」提案，且带四道安全检查——goal 必须钉版本（infer 不翻）、链上 brief 双向查 {{node.X.output}} 数据引用（有真依赖就不许并）、以spec 图为真相核对链形、补丁 all-or-nothing。触发不了就静默跳过，产出仍是 pending 提案，永不自动发布。其余八类 finding 一律人工翻译——LLM+P 分工：模型只建议，合法性交给确定性校验器23。
  • 同题 A/B：没有评测集之前，复测=人挑两个可比的 goal 分别钉 v1/v2 跑同类任务，A/B 卡并排七项指标 + Δ。采纳标准不是"全面变好"而是效率指标改善且质量指标不掉。

6.3 入口坡道：涌现固化（infer → blueprint 的收敛通道）

infer 执行goal 不绑蓝本，owner 动态拆解（弹性全保留）
→
签名记录每次 done 都记形状签名进 infer_shape（L1 精确 + L0 骨架）
→
3 次同构同域连续 3 次签名全等 → 判定"这已经是事实上的固定流程"
→
自动起草 v1确定性翻译执行图→蓝本草稿（只起草，永不自动发布）

这是「第三派动态多 agent」向「图即代码」收敛的通道1127：弹性先自由地试，试出稳定形状后沉淀为可版本化、可 diff、可优化的规范。起草名撞名即跳过（签名即命名键，天然去重不堆积）。

人工闸门清单——闭环里永远属于人的四个按钮 批准提案（机器只许起草）· 发布版本（草稿永远不生效）· 采纳结论（A/B 只呈现证据，不替人拍板）· gate 拍板（超时有兜底分支，但默认等人）。自动化的上限被明确设计在这里：平台永远不机器自批机器提案2025。

7指标考核：四层金字塔与诚实边界

层内容作用
第 1 层
执行图指标		结构（node/edge/depth/lane）、时间（wall / critical_path / work_sum / serialization_loss）、并行（parallel_speedup=work_sum÷wall）、等待拆分（dependency / dispatch / queue / human_wait）、质量（rework_ratio、retry_amplification、verify_rounds、verify_overhead_ratio、review_busy、consult_count）单次执行的体检报告；RSI 分析与 A/B 的原始数据
第 2 层
A/B 比较集		七个键（有序）：critical_path_ms · wall_ms · parallel_speedup · rework_ratio · verify_pass_rate · verify_overhead_ratio · human_wait_ms版本间可判定对比——质量指标（一次通过率）与效率指标并列，防止"更快但更烂"
第 3 层
RSI 九类结构发现		serial_chain（人为串行）/ split_candidate（重节点该拆）/ lost_parallelism（并行潜力流失）/ merge_candidate（小兄弟聚尾）/ wrong_assignee（派错人）/ retry_amplification（重试放大）/ ping_pong（来回踢）/ brief_quality（简报太烂）/ consult_repeat（重复咨询）把"哪里不对"翻译成"哪个 finding 类别 + 建议"，每条带证据与置信级24
第 4 层

  • verify_pass_rate（Phase D 落地）：一次通过率 = verified 节点中 Reworks==0 的占比（数据源=verification_result/sub_goal 表，零新埋点）。cost_per_success 诚实缺席：run 表没有 token/成本列，平台不造数——什么时候接入计费，什么时候这个键才出现。

8收敛条件怎么定义

8.1 涌现固化的收敛：双层签名（§14.1）

收敛判定不引入任何 LLM 判断，两层都是确定性多重集哈希，可解释可复现：

镜头看什么收敛条件触发动作
L1 精确全部节点 kind 多重集 + (from|to|edge) 三元组多重集同域最近 3 条 全量同构起草「固化：签名·域名」
L0 骨架剥掉运行间噪声：verify/review/consult 节点、seq/verified_by/consult 边3 条骨架同构（L1 允许不同——多一轮咨询、一次返工不再破坏收敛）起草「近似固化：骨架签名·域名」
  • 近似固化按 L0 骨架签名为命名键——后续 near-miss 继续去重进同一份草稿，不堆积；
  • 两层都只起草、不发布：误命中最坏结果=多一份等人审的零风险草稿（宁欠勿滥）；欠触发代价也为零（infer 弹性全在，不收敛就不固化，没有任何损失）；
  • 诚实标注：多重集签名是便宜的滤网，不是图 canonization——它做的是"够用的收敛检测"，不是"形状等价判定"。

8.2 迭代轮次上限：rsi.max_auto_rounds（§14.2）

  • 配置在 app_settings 表，默认 10；0=关闭自动产出；改完即生效，无需重启。
  • 只封机器的自动工件：涌现固化按域计（infer_shape.drafted 行数）、翻译器按 distinct blueprint 计（pending/approved 的 rsi-translator 提案）。
  • 分析永不被封（可见性不倒退：finding、报告、metrics 照常产出）；人工动作永不在内（人批多少提案、发多少版本都不限）——上限防的是"机器自己刷自己"，到上限只记日志跳过，不报错不断流。

8.3 采纳的收敛与未来条件（Phase E 立项）

  • 现在：采纳=同题 A/B 七项指标支持假设（效率改善且质量不掉）+ 人拍板发布。
  • Phase E 评测集（§14.3）：domain 声明 eval_goals 题库，mode=eval 对每道题两版本各真实跑一次，聚合从单对 delta 升级为集合均值 + 符号显著性检验（min_pairs=5 才有结论）27，达标才允许采纳建议。成本诚实说明：复测=真实执行=花钱花时间，这正是它没有被塞进本轮的原因。
  • Phase E best checkpoint（§14.4）：版本链已经是全量 checkpoint，缺的只是"哪个最好"的标注——补 blueprint.best_version_id 人工列、A/B 卡「设为最佳」、列表徽章、绑定默认选中。语义边界：标注不是开关，不自动切流量。AFlow 调研的教训：checkpoint 的价值在检索与复用，不在存储1819。

10终章：一个完整迭代的实践案例

以下用一个虚构但机制严格对齐的 Go 服务维护团队（域 go-service，小队 go-dev-squad：队长 go-owner、两名 implementer、一名 reviewer），把前面所有章节串成一条时间线。数字为演示数据，每一幕都标注了它演示的机制。

第 0 幕 · 自由生长：三次 infer 执行演示机制：infer 弹性 · 形状签名记录 · 运行间噪声（→ 第 6.3 / 8.1 节）

团队尚未绑任何蓝本。三个线上 bug（#114、#117、#121）先后交给 owner，它每次都临场拆成三步：复现 → 修复 → 验证，拆解略有差异但骨架一致。第三次（#121）修复前 owner 还向队长发起了一轮 consult——多出来的咨询就是「运行间噪声」。

每次 goal 跑到 done，平台记一条形状签名进 infer_shape：L1 全量签名三次不全等（#121 多了 consult 节点），但 L0 骨架签名——剥掉咨询/验证/评审噪声后——三次全等。

第 1 幕 · 涌现收敛：自动起草「近似固化」演示机制：L0/L1 双层签名 · 只起草不发布 · 人工审查补强（→ 第 2、8.1 节）

#121 终态落账的瞬间，收敛条件命中：同域最近 3 条 L0 骨架同构。蓝本列表里自动出现一份草稿：

名称：近似固化：a3f9c210·go-service
描述：自动起草（近似固化）：同域连续 3 个 infer 执行图骨架同构（细节有差异），
      由平台确定性翻译生成（§14.1 L0 骨架收敛）。请审查后发布；发布前不影响任何任务。
结构：t_repro(复现) → t_fix(修复) → t_verify(验证) → end_ok

机器不做的事，人做：go-owner 审查这份草稿，补上它看得到而签名看不到的东西——给三个 task 都加上 verify.mode=machine（域里冻结的 Checks：跑测试、查竞态），给 t_verify 配 verifier=reviewer（Player-Referee：修复者不能自己验自己），t_fix 的 brief 写上 {{node.t_repro.output}}（修复必须引用复现结论）。逐项校验通过 → 发布 v1。

从这一刻起，go-service 的新任务有了一种新选择：不绑蓝本=继续自由拆解（第 0 幕模式）；绑 v1=享受确定性保证。

第 2 幕 · 图说了算：一次被守卫护航的执行演示机制：两拍编译 · guard · 结构拒绝 · 死分支剪除（→ 第 2.4、4 章）

bug #131 进来，goal 绑 v1 激活。编译拍 1：3 个 sub_goal 一次全部建出（t_repro 立即开跑，t_fix/t_verify 按 depends_on 挂起）；拍 2：t_repro verified、t_fix 被释放的瞬间，brief 里的 {{node.t_repro.output}} 解析成复现结论的快照。

中途 owner 试图 subgoal create 加一个「顺手写个补丁说明」的子项——被结构拒绝挡回："goal is blueprint-driven: sub-goals are compiled from the blueprint, not created ad hoc"。它改用在目标下评论转达想法（契约允许的汇报通道）。

t_verify 的机器验收第一轮没过（竞态检查 fail），重试第 2 轮通过。goal 完成时守卫核对：规范图 4 个节点全 settle（3 个 settled + end_ok）→ 放行 done。任务页并排两张图：teal 的规范图（计划）与蓝色执行图（记录），形状完全一致——这就是双簿记给人看的形态。

第 3 幕 · 发现与提案：机器的安全边界 + 人的翻译演示机制：RSI serial_chain · 翻译器数据流守卫 · 人工结构化补丁 · 三色 diff（→ 第 6.2 节）

训练分析对 #131 的执行图跑 RSI：关键路径 6 个节点（3 task + 3 verify）≥ 阈值 4 → 产出 serial_chain finding：「复现→修复→验证被人为串行化」。

Phase D 翻译器先试：把链上的 task 映射回 spec 节点 → 数据流检查发现 t_fix 的 brief 含 {{node.t_repro.output}}——存在真实数据依赖，翻译器正确地放弃自动提案（数据流守卫生效，宁可不提也不提错）。机器知道自己的边界。

人来翻译：go-owner 读 finding，做出机器做不到的语义判断——「复现」里其实含两件事：搭修复分支环境（与复现无数据依赖，可提前并行）和「跑出最小复现」（修复的硬依赖）。手工起草结构化补丁提案：

提案标题：环境准备与复现并行化
hypothesis：把环境搭建从复现中拆出并行，缩短关键路径（expected: critical_path_ms ↓）
patches：
  - op: add_node   node: { id: t_env, type: task, title: 搭建修复分支环境, … }
  - op: add_edge   edge: { source: t_env, source_handle: "done", target: t_fix }
  - op: update_node node: t_repro（brief 收窄为纯复现）

创建时补丁立即应用过 V1–V6（合法入库），批准后以假设为 changelog 开出 v2 草稿。A/B 前他又给 v2 加了一个 gate 节点（「高风险修复须人确认」，timeout 24h→reject）——把第 2 幕里靠人盯 IM 的隐性等待，变成图上的显性卡点。发布 v2。

第 4 幕 · 同题 A/B：证据说话，人拍板演示机制：ABMetricKeys 七项 · 质量与效率并列（→ 第 6.1/7 章）

两个同类 bug（#135、#138）分别钉 v1、v2 各跑一次。蓝本详情页 A/B 卡：

指标goal A（v1，#135）goal B（v2，#138）Δ（B−A）读数
critical_path_ms61 min44 min−17 min并行化兑现
wall_ms74 min51 min−23 min端到端缩短 31%
parallel_speedup1.081.42+0.34并行度提升
rework_ratio0.330.17−0.16gate 拦下高风险返工

结论不是"全面变好"——wall 与质量指标改善，human_wait 上升 6 分钟。go-owner 的采纳理由写在批准里：「质量换等待，值得」。这是 A/B 的正确打开方式：它呈现证据（含代价），不替人拍板。v2 发布，v1 原样留在版本链上——任何时候新 goal 钉回 v1 即回滚。

第 5 幕 · 环境继续收敛（展望）演示机制：迭代上限 · Phase E 的两个候选能力（→ 第 8.2/8.3 节）

闭环继续滚动：若后续又出现 3 次新形状的同构执行，会再起草一份近似固化草稿——但该域 drafted 计数已 +1，自动产出向 rsi.max_auto_rounds（默认 10）逼近；到达上限后机器只记日志不再自动起草，而人随时可以继续：人工提案、批准、发布不受任何限制。RSI 分析与指标照常产出——被封的只有"机器自动开新工件的笔"，不是"机器的眼睛"。

Phase E 落地后的后续剧本：go-service 域声明评测集 {#131, #135, #138, #142, #146…}，mode=eval 让 v3 候选对整个题库自动复测，集合均值 + 符号检验（5 对起判）替代手工挑题；跑赢后在 v3 上点「设为最佳」，列表页挂出「最佳 v3」徽章，新任务绑定时默认选中——版本链这台"仓库"终于有了检索索引。

这条时间线就是平台的自我描述：infer 自由地长（第 0 幕）→ 骨架收敛成规范（第 1 幕）→ 规范被结构强制地执行（第 2 幕）→ 执行反过来优化规范（第 3–4 幕）→ 优化被护栏与人的拍板权约束着滚向下一轮（第 5 幕）。图说了算，而图本身，也是可以被锻造的。

▤注解与出处：每个结论从哪来

正文里凡带 n 上标的地方，对应下面这条注解。分四组：① 为什么顺序不能靠提示词、② 业界把顺序收回代码的实证、③ 图 / 版本 / 分析的产品形态、④ 自迭代的学术谱系，末尾附本仓库依据（所有机制描述都能在提案与代码里逐一核对）。只标一手出处；灵感来源 ≠ 照搬——多数条目是「同一个问题别人怎么解」，借鉴的是思路与约束，不是代码。

① 为什么「顺序靠提示词」必然不稳

  1. 1OpenAI · Structured Outputs（2024-08） —— 受约束解码把「只能输出合法 JSON」变成解码器事实：官方对比是 prompting 遵从率 <40%、受约束解码 100% 合法；发布文同时承认模型行为 inherently non-deterministic。 用在哪：s0「提示词是概率指令」；2.2 router（LLM 只能从注册类里选，枚举 schema 收口）。 openai.com/index/introducing-structured-outputs-in-the-api
  2. 2Liu et al. · Lost in the Middle（2023） —— arXiv:2307.03172。相关信息落在长上下文中部时，模型表现显著下降（首尾最好、中间最差）。 用在哪：s0 痛点①——长 playbook / 长简报里的中段指令最容易漏，这是「漏跑」的机制级解释，不是执行者不认真。 arxiv.org/abs/2307.03172
  3. 3Zhou et al. · IFEval（2023） —— arXiv:2311.07911。指令遵从是可与知识、推理分开测量的独立能力维度（可用可验证的约束程序化打分）。 用在哪：s0 痛点①——「它这次听了，下次不一定听」是可测的遵从率问题，而不是主观体感；所以治法是把权威搬出提示词，而不是把话说得更重。 arxiv.org/abs/2311.07911
  4. 4Anthropic · Building Effective Agents（2024-12） —— 三个观点被直接采纳：① 自主性意味着错误在多步之间复合，成本/延迟换性能，所以必须给停止条件；② prompt chaining 里的 gate 应当是纯代码检查而非再开一个 LLM 问「你觉得对吗」；③ ACI / poka-yoke——不想让模型做的事，就不要把它做成模型能调用的工具。 用在哪：2.2 弹性三口袋、4 章非蓝图场景的上限、5 章「提示词退回擅长表达的位置」。 anthropic.com/engineering/building-effective-agents

② 业界把「顺序」收回代码的实证

  1. 5LangGraph · supervisor 库退场 —— 官方注记原文："We now recommend using the supervisor pattern directly via tools rather than this library for most use cases. The tool-calling approach gives you more control over context engineering." 迁移指南把 supervisor 改成 create_agent(model, tools=[call_worker_a, call_worker_b])——编排者的工具面里只剩委派。 用在哪：4 章闸门②「契约换岗」——不是把「请委派」写得更大声，而是把业务工具从它手里拿走。 docs.langchain.com/oss/python/migrate/langgraph-supervisor
  2. 6n8n 1.82.0 · 废弃 LLM 流程编排类型 —— 曾经的 Conversational / OpenAI Functions / Plan-and-Execute / ReAct / SQL 等编排类型全部废弃，收敛为单一 Tools Agent：外层顺序归画布，LLM 只做节点内的工具选择。 用在哪：4 章、5 章——「让 LLM 直接编排步骤」这条路线，连最主张低代码的平台都退回了。 docs.n8n.io/.../n8n-nodes-langchain.agent
  3. 7Temporal · 确定性重放 —— Workflow 代码必须确定性可重放；LLM 调用被官方归类为 Activity（"Activities handle everything that interacts with the outside world, like: API calls, Database queries, LLM invocations"）；Event History 是唯一真相，崩溃后重放历史而不重跑已执行的调用。 用在哪：1.2 双簿记——「执行图是记录、永不可编辑」与 Temporal「历史即事实」同源；也解释了为什么记录不能被优化器改写。 docs.temporal.io/workflows · learn.temporal.io/tutorials/ai/durable-ai-agent
  4. 8agentevals · 轨迹断言 —— strict（工具调用同序精确匹配）/ superset（至少调完参考里的全部工具，治漏跑）/ subset（不许多余调用，治越权）/ unordered。 用在哪：4 章闸门④；7 章「从事后测量到结构性不可能」——蓝图模式让前两个断言从「测」变成「发生不了」，subset 仍留作对「多跑一步」的兜底。 github.com/langchain-ai/agentevals
  5. 9Magentic-One（Microsoft Research, 2024） —— arXiv:2411.04468。双账本：Task Ledger（计划与事实）+ Progress Ledger（每步自检：进展如何、是否停滞）；停滞即触发重规划。 用在哪：4 章 amber 框——infer 模式保留动态拆解，但必须带账本与停滞检测，否则弹性变成失控。 arxiv.org/abs/2411.04468
  6. 10Microsoft Agent Framework · Magentic 编排的旋钮 —— WithMaxRounds(10)、WithMaxStalls(3)、WithMaxResets(2)、RequirePlanSignoff(bool)；官方 Sequential / Concurrent / Handoff / Group Chat 之外，Magentic 是唯一「manager 动态协调」的一等公民。 用在哪：4 章 amber 框的四个默认值（10 / 3 / 2 / 计划签核）直接照此对齐。 learn.microsoft.com/.../orchestrations/magentic
  7. 11LangGraph · 官方混合模式 —— "Build bespoke execution flows with LangGraph, mixing deterministic logic and agentic behavior. Embed other patterns as nodes in your workflow."（多智能体五模式里唯一被称为「定制工作流」的一档） 用在哪：2.2 弹性口袋、6.3 涌现固化——本项目的「确定性外壳 + 受控弹性节点」不是发明，是这条官方路线走到了版本化与可优化。 docs.langchain.com/oss/python/langgraph/workflows-agents

③ 图、分支编码、版本与分析的产品形态

  1. 12Dify · 工作流 DSL —— 图以 YAML 序列化（ReactFlow 结构的导出）；关键约定：分支的可达路径编码在 edge 的 sourceHandle（if-else 用 case ID、question-classifier 用 class ID、human-input 用 action ID），「可选分支集合」是图数据的显式字段。 用在哪：2.1 读图规则——分支不写在文字里，写在端口上；本项目 source_handle 同此约定，所以 V1/V3 能把「声明了却没接」挡在发布门。 docs.dify.ai · github.com/langgenius/dify
  2. 13Dify · 版本三态 —— Current Draft（编辑区，不影响线上）→ Latest Version（线上运行态）→ Previous Versions（可恢复、可导出、可命名 + release note），付费版可按指定已发布版本运行（这同时是 A/B 的基础设施）。 用在哪：2.4 版本模型——draft / published / NewDraft(vN+1) 三态与「per-goal 钉版本」。 docs.dify.ai
  3. 14Coze · 子工作流引用钉版本 —— 被引用方发布新版本不会让引用方自动升级（生产隔离的正确做法）；Coze 亦有工作流版本历史与回滚。 用在哪：2.4「发布版本=回滚锚点」；8.3 的 A/B 与回滚语义都依赖「旧版本永远可再跑」。 coze.com/open/docs/guides/workflow_version
  4. 15LangGraph · interrupt + checkpointer —— interrupt(payload) 在节点内暂停，checkpointer 保存完整状态，恢复时以 Command(resume=value) 回到同一 thread——暂停点就是图节点，恢复就是结构化响应。 用在哪：2.2 gate 节点——「等人拍板」被做成图里一个持有者节点（永不入队执行），而不是提示词里一句「不确定时先问」。 docs.langchain.com/oss/python/langgraph/interrupts
  5. 16Airflow · @task.branch —— 分支函数返回下游 task_id（或 None 全跳过），纯确定性；DAG 本身由代码定义、UI 只读渲染。 用在哪：2.2 condition——「分流是编译期确定性求值」这条，与 Airflow 的 branch 语义一致（不是 LLM 猜）。 airflow.apache.org/.../core-concepts/dags
  6. 17LangGraph · 图导出 —— get_graph() 可导出结构化图（JSON），并可渲染 Mermaid / PNG；Dify、CrewAI（flow.plot()）也都能从结构直接出图。 用在哪：2.1 与前端渲染——结构是真相，图是它的一个视图；本项目的规范图、执行图共用同一渲染器（一渲染器两种味道）。 docs.langchain.com/oss/python/langgraph/visualize-graphs
  7. 24LangSmith · Insights —— 异步分析是成熟产品形态：后台 job（≤30 分钟）、双模型分工（聚类 + 摘要）、样本上限 1000 trace、报告带百分比 + 可点回具体 trace 的证据链。 用在哪：7 章第 3 层——RSI 的 finding 不是一次性聊天回答，而是有状态、可调度、可复核的后台实体。 docs.langchain.com/langsmith/insights
  8. 25Braintrust · Loop / Patterns —— 每条「发现（pattern）」都是有状态实体：带证据、解释、建议、severity、受影响 trace 数；会被刷新，行为连续两个工作日不再出现即自动关闭；可一键转成 scorer / 分类器 / 编码任务。其原文边界：「Loop 读操作不打断人，写操作（改 prompt、建 dataset、开 PR）要人批准」。 用在哪：6 章人工闸门——「发现可自动积累、工件必须人批」这条分工；以及 finding 的生命周期设计。 docs.braintrust.dev/observe/patterns
  9. 26n8n History / Zapier Copilot / Dify Build-by-Chat —— 三家的共同点：改动前自动快照、改动后可视化 diff（n8n Reviews 直接画节点与连线的增删）、以及逐条采纳（Dify 的 Apply / Discard、Zapier 的 checkpoint + revert 对比框）；发布是独立闸门，不随编辑发生。 用在哪：6.2 三色 diff 与「批准=开新草稿，不自动发布」——把「AI 改图」做成可回退的编辑动作，而不是一次不可逆的重写。 docs.n8n.io/.../workflow-components · docs.dify.ai
  10. 27本仓库调研结论（一手整理） —— docs/research/rsi-industry.md：平台能力呈「埋点 → 面板 → 分析 → 优化」四级阶梯，多数产品停在二三级；「自优化闭环不是训练模型，而是 trace → 数据集 → 评测 → 改 prompt/策略 → 复测」。docs/research/rsi-summary.md：工作流三派（画布低代码 / 图即代码 / 动态多 agent）与「策略 + 运行时涌现」的取舍。 用在哪：6.3（涌现固化=从第三派向图即代码收敛）、7 章第 4 层（优化器自身也要被度量）、8.3（评测集与统计功效）。 docs/research/rsi-industry.md · docs/research/rsi-summary.md

④ 自迭代的学术谱系（本项目的设计都对应其中一支）

  1. 18AFlow（2024） —— arXiv:2410.10762。把 workflow 表示为代码图，用 MCTS + 代码修改搜索；6 个数据集平均 +5.7%，成本仅为 GPT-4o 方案的 4.55%。前提：图必须能序列化、能被程序改写——这正是本项目把蓝本做成 JSON 的原因。 用在哪：8.3 checkpoint 的教训（价值在检索与复用）、以及「结构化先于优化」的立论。 arxiv.org/abs/2410.10762
  2. 19ADAS（2024）/ DGM（2025） —— arXiv:2408.08435（meta agent 写新 agent、递增 archive）/ arXiv:2505.22954（archive + 树状开放探索，SWE-bench 20.0%→50.0%）。共同结论：archive 是抗退化的结构，只留「当前最优」的单点爬山一旦进入平台期就回不去。 用在哪：8.3——版本链就是本项目的 archive；best checkpoint 只是给它加索引，而不是新增存储。 arxiv.org/abs/2505.22954 · arxiv.org/abs/2408.08435
  3. 20STOP（2023）/ Gödel Machine（2003） —— arXiv:2310.02304（让改进器改进自己，LM 自发提出 beam / GA / 模拟退火）/ arXiv:cs/0309048（要求改写前先证明净收益）。后者理论优雅但实践不可行，所有能跑的工作都退回到「在基准上实测」。 用在哪：6 章人工闸门——「机器不许自批机器」不是保守，是这条谱系唯一的可行边界；也解释了为什么本项目用「经验验证 + 统计」而不是证明。 arxiv.org/abs/2310.02304 · arxiv.org/abs/cs/0309048
  4. 21DSPy（2023）/ TextGrad（2024） —— arXiv:2310.03714（按 metric 编译 prompt 与 demonstrations，编译集/验证集分离，超 few-shot >25%）/ arXiv:2406.07496（把「文本反馈」当梯度反传，类 PyTorch 组合）。 用在哪：6.2 操作符谱系的「参数级 / 文本级」两支——本项目不做参数训练，改的是图结构与节点配置，但这支给出了「优化什么由可测指标定义」的先例。 arxiv.org/abs/2310.03714 · arxiv.org/abs/2406.07496
  5. 22GPTSwarm（2024）/ AgentSquare（2024） —— arXiv:2402.16823（agent 本身是可优化的计算图：节点级调 prompt、边级增删拓扑）/ arXiv:2410.06153（模块化搜索空间 + 性能预测器）。前者是「把图当优化对象」最贴近本项目的一支。 用在哪：6.2 的五个操作符——add/delete node 与 add/delete edge 正是上面这组「节点级 + 边级」动作的直接对应。 arxiv.org/abs/2402.16823 · arxiv.org/abs/2410.06153
  6. 23LLM+P（2023）/ LLMCompiler（2023） —— arXiv:2304.11477 的立场句："so far, LLMs cannot reliably solve long-horizon planning problems"，于是 LLM 只做 NL↔PDDL 翻译、规划交经典规划器（输出保证正确/最优）；arXiv:2312.04511 一次性把任务编译成 DAG 并行调用。 用在哪：6.2 确定性翻译器——LLM 只负责「把意图翻译成结构」，合法性（无环、依赖存在、端口对得上）交给确定性校验器；并行化提案即 LLMCompiler 的思路。 arxiv.org/abs/2304.11477 · arxiv.org/abs/2312.04511
